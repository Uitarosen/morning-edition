GitHubに
1万個の

リポジトリが潜伏

セキュリティ研究者のOrchidが「1万を超えるGitHubリポジトリがトロイの木馬マルウェアを配布していた」という調査報告を公開し、592ポイント・136コメントという大きな反響を呼んでいます。これらのリポジトリは正規の人気オープンソースプロジェクト（PyPI・npmライブラリ、開発ツール、ゲームハック等）を偽装し、本物のリポジトリと見分けがつきにくい状態でマルウェアを配布していました。攻撃者のテクニックは巧妙で、Starの数をボットで水増しし、READMEは本物のプロジェクトをほぼそのままコピー、コミット履歴も偽造していました。実際のマルウェアは難読化されたPythonスクリプトやバッチファイルとして混入されており、実行するとシステム上の暗号通貨ウォレット・ブラウザの保存済みパスワード・環境変数（APIキーを含む）を窃取して攻撃者のサーバーに送信します。GitHubはOrchidの報告を受けてリポジトリを削除し始めていますが、ピーク時には1万件を超える偽リポジトリが存在していたとのことです。HN上では「SupplyChain攻撃の亜種——typosquattingはパッケージ名のスペルミスを狙うが、これはGitHubリポジトリのクローン自体を悪用する」「READMEが本物と同じでStarも多いと、経験のある開発者でも騙される——Starを信頼指標にするのが危険だと分かる」「自分のCI/CDパイプラインが知らぬ間に偽リポジトリを参照していないか確認すべき——lockfileの厳密な管理と公式URLの直接指定が防衛手段」「GitHubが自動検出できなかったのは、リポジトリ単体では悪意あるコードが少量に分散されていてスキャンをすり抜けるため」「依存関係のハッシュ検証（Content Addressing）が最も確実な対策——SupplyChain攻撃の根本的な解決策」という136コメントが展開中です。
攻撃の仕組み
人気OSS（開発ツール・ライブラリ・ゲームツール）を偽装した1万超のGitHubリポジトリを作成。Starをボットで水増しし、READMEは本物をコピー。難読化されたマルウェアを同梱し、インストール・実行するとAPIキー・パスワード・暗号通貨ウォレット情報を窃取して攻撃者サーバーへ送信
今すぐできる防衛策
①依存関係は公式ドキュメント記載の公式URLから取得②lockfile（package-lock.json, poetry.lock等）をコミットしハッシュ固定③`git log --all`で怪しいコミット履歴がないか確認④GitHub Stars数は信頼指標にしない——ボット水増しが容易⑤CI/CDパイプラインの依存関係スキャン（dependabot, snyk等）を活用
根本的対策：コンテンツアドレス
URL（リポジトリ名）ではなくコンテンツのSHA256ハッシュで依存関係を特定する方式がSupplyChain攻撃への根本解。Nixパッケージマネージャー・Cargo（Rust）・Go modulesはハッシュベースの固定が充実。npmやpip環境では意識的にlockfileとハッシュ検証を使う必要がある

DEVELOPER TOOLS / GIT / ACTIONABLE — .gitignoreだけじゃない！Gitのファイル無視機能には他にも方法が存在することを解説した記事が241ポイント・73コメントで話題

.gitignoreだけじゃない——
Gitのファイル
無視機能を
全部知る

「.gitignore Isn't the Only Way to Ignore Files in Git」というタイトルのブログ記事が241ポイント・73コメントを集めています。多くのエンジニアが.gitignoreだけを知っていますが、Gitには実は複数のファイル無視メカニズムが存在し、それぞれ異なるスコープと用途を持っています。記事では①`.gitignore`（リポジトリ内・共有設定）②`.git/info/exclude`（ローカルのみ・非共有）③グローバル`.gitignore`（`core.excludesFile`設定・全リポジトリに適用）④`git update-index --skip-worktree`（追跡済みファイルへの変更を無視）⑤`git update-index --assume-unchanged`（パフォーマンス用・ローカルのみ）の5つを比較解説しています。特に実用的なのは「`.git/info/exclude`：自分だけが使うエディタ設定ファイルや個人ツールの出力をチームの.gitignoreを汚さずに除外できる」「`--skip-worktree`：設定ファイルをリポジトリ管理しながらローカル値を追跡させない（例：開発用のlocal overrideを本番用ファイルに混ぜない）」という2つのユースケースです。HN上では「`--skip-worktree`はdotfilesやconfig管理で長年使っていたが、チームメンバーに説明するのが難しいのが欠点」「グローバル.gitignoreに`.DS_Store`や`.idea/`を追加することは誰もが一度はやるべき設定——.gitignoreに個人設定を混ぜるのはチームへの迷惑」「`--assume-unchanged`は大規模リポジトリでの`git status`高速化に使われることがあるが、副作用も多い——用途をよく確認してから使うべき」「git sparse-checkoutも実質的なファイル無視として使えるケースがある——大規模モノレポでの部分チェックアウト」「この記事を見て初めて`core.excludesFile`の設定をした——10年gitを使っていても知らないことがある」という73コメントが展開中です。
5つのファイル無視メカニズム
①`.gitignore`（リポジトリ内・チーム共有）②`.git/info/exclude`（ローカルのみ・非共有）③グローバル`.gitignore`（全リポジトリ・`git config --global core.excludesFile ~/.gitignore_global`で設定）④`--skip-worktree`（追跡済みファイルへの変更無視）⑤`--assume-unchanged`（パフォーマンス優先の変更追跡停止）
今すぐ使える設定：グローバル.gitignore
`git config --global core.excludesFile ~/.gitignore_global` を実行後、`~/.gitignore_global`に`.DS_Store`, `.idea/`, `.vscode/settings.json`, `*.swp`, `node_modules/`等を追加。チームの`.gitignore`を個人ツールの設定で汚さずに済む——一度設定すれば全リポジトリに適用される
skip-worktreeの使いどころ
本番用設定ファイル（`config.yaml`等）をリポジトリで管理しながら、ローカル開発時だけ異なる値を使いたい場合に有用。`git update-index --skip-worktree config.yaml`で追跡を停止。ローカル変更が`git status`に出なくなる。解除は`--no-skip-worktree`

強制同意（Forced Consent）とは
サービス・製品・機能の提供を、マーケティング目的のデータ利用への同意に紐付ける慣行。「同意しないと使えない」という状況はGDPR第7条の「Freely Given（自由意志に基づく）」要件を満たさず、その同意は法的に無効。Elkjopは会員登録・購入時にこの形式の同意を要求していた

トークン圧縮の問題点
プロンプトのトークン数を削減する「圧縮」アプローチは、会話的テキストでは要約が機能する場合があるが、コード・数式・構造化データ・仕様書では情報損失が精度劣化に直結する。「コスト削減」を理由に重要な情報を切り捨てると、モデルの回答品質が低下しROIが下がる
