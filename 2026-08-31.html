Creepy Crawlies——
カーネルコミッターが
語る「気持ち悪いもの」

kernel.orgのインフラセキュリティを担うKonstantin Ryabitsev（monsieuricon）が投稿した「Creepy Crawlies」が780ポイント・362コメントという本日最大の反響を呼んでいます。タイトルが示すとおり、Linuxカーネルや周辺のオープンソースインフラで見つかった「ぞっとするような」セキュリティの弱点や設計上の奇妙な挙動について論じた記事です。monsieuricon氏はカーネル開発のメール署名基盤（b4、patatt）の開発者としても知られており、その視点からサプライチェーンセキュリティや信頼チェーンの脆弱性を平易な言葉で解説しています。 HNでは「読んでいて背筋が寒くなる」「これはすべてのシステム管理者が読むべき」というコメントが相次ぎ、カーネルインフラの信頼性に関する広範な議論が巻き起こりました。セキュリティ研究者・カーネル開発者・システム管理者の三者それぞれの視点から多角的な意見が寄せられています。
記事の核心
「安全に見えるものが安全でない」設計上の問題
Ryabitsev氏がカーネルインフラで発見した問題は「バグ」ではなく「設計上の前提が崩れた状態」。特に暗黙の信頼関係に依存するコンポーネントが、現代の脅威モデルに対して脆弱になっている点を指摘。SolarWinds以降、ソフトウェアサプライチェーンへの関心が高まる中での重要な警鐘。
HNコミュニティの反応
「xz-utils事件を思い出した」
2024年に発覚したxz-utils backdoor事件（Jia Tan事件）と重ねて論じるコメントが多数。「オープンソースの透明性は必要条件だが十分条件ではない——信頼できるメンテナーの確保と鍵管理が同様に重要」という議論に発展。カーネルコミュニティのsigstore/b4移行についても言及あり。
実践的な教訓
「見えないバックチャネルを疑え」
HNでまとめられた教訓：①エラーメッセージや例外ハンドラーはデータ漏洩のサイドチャネルになり得る②「読み取り専用」の処理でも意図しない状態変化が起きる場合がある③信頼境界は明示的に定義されなければ暗黙のうちに崩れる。自分のコードベースを「Creepy Crawlies」の目で見直すよう推奨するコメントが多かった。

HuggingFaceハックの
ポストモーテム——
METRとRedwood
Researchが分析

Zvi Mowshowitzがthezvi.wordpress.comで紹介したMETRとRedwood Researchによる「HuggingFaceハックのポストモーテム」が187ポイント・128コメントを集めました。AIモデルのハブとして広く利用されているHuggingFace Hubで発生したセキュリティインシデントについて、AIセーフティ研究機関の視点から何が起きたのか・何が失敗したのか・何を学ぶべきかを詳細に分析した内容です。 HuggingFaceはPickleファイルやモデルウェイトを通じた悪意あるコードの混入問題を以前から抱えており、Safetensorsフォーマットの普及推進も行ってきましたが、このインシデントはより組織的な攻撃の側面を持つと報告されています。METRとRedwood Researchという二つのAIセーフティ機関が共同でポストモーテムを実施した点が注目されています。
インシデントの概要
HuggingFace Hubへの攻撃：悪意あるアクターがモデルリポジトリにPickle形式のファイルを混入させ、ダウンロード時に任意コードが実行されるよう細工したとされる。規模：何千人ものユーザーが影響を受けた可能性があり、特にモデルをダウンロードして直接ロードした開発者・研究者が対象。既知のリスク：Pickleによる任意コード実行はAI/MLコミュニティで長年指摘されてきた問題で、今回のインシデントはそのリスクが現実になったケース。
METRとRedwoodの分析ポイント
ポストモーテムが特定した失敗点：①HuggingFaceのスキャンインフラが悪意あるPickleを十分に検出できていなかった②ユーザーへの信頼表示（verified/unverified）が実際のリスクを反映していなかった③Safetensorsへの移行が完全でなく、レガシーフォーマットが依然として広く使われていた。改善提案：コンテナ隔離環境でのモデルロード・コミュニティ主導の評判システム・モデル来歴の検証強化（SBOMのAI版）。
開発者が今すぐできること
実践的な防御策：①`torch.load()`に`weights_only=True`を常に指定する（PyTorch 2.0以降）②HuggingFace製のsafetensors形式のみを使用する③モデルは分離された仮想環境または専用コンテナでロードする④出所不明のモデルはHuggingFaceスペースのサンドボックス内でのみ試用する。HNコメント：「AIモデルはコードだ——ダウンロードして実行することはコードを実行することと同義であり、同等のセキュリティ意識が必要」という認識をコミュニティに広めることが課題。

プライバシー / 暗号化 / EU / ProtectEU / バックドア / 法執行 / 政策 / デジタル権利 — EUがProtectEU戦略で暗号化バックドアを再び推進。309ポイント・124コメント。2026-08-31

EU、暗号化バックドアを
再び推進——
ProtectEU戦略
の衝撃

欧州委員会が「ProtectEU」戦略の一環として、法執行機関が暗号化通信にアクセスできるようにするバックドア法制化への動きを再び活発化させていると報告され、309ポイント・124コメントを集めました。「Chat Control」と呼ばれる以前の試みが2024年に頓挫した後、EUはアプローチを変えて再度立法を目指しているとのことです。 暗号化バックドア問題は技術者・プライバシー擁護者が長年にわたって反対してきた政策論争です。「悪人だけがアクセスできるバックドアを作ることは技術的に不可能——バックドアは誰にでも使われる」という論理は専門家コンセンサスですが、政治的な圧力は繰り返し浮上します。Signal・ProtonMail・Wickrなどのエンドツーエンド暗号化サービスへの影響が特に懸念されています。
ProtectEUとは何か
EUの内務・司法担当のフォン・デア・ライエン欧州委員会が打ち出した包括的なセキュリティ戦略。テロ対策・組織犯罪対策・サイバーセキュリティ強化を名目として法執行機関の権限拡大を図る。暗号化へのアクセス要件はその一部として含まれており、「技術的ソリューション（バックドア）の義務付け」ではなく「法執行機関との協力義務」という形式をとることで以前の反発を回避しようとしていると分析される。
なぜ技術者が反対するのか
数学的な問題：暗号化には「善い人だけが通れる裏口」は存在しない。バックドアは欠陥であり、発見した者（政府・犯罪者・外国諜報機関）が使用できる。実例：NSAが2013年に設計した乱数生成アルゴリズム「Dual EC DRBG」のバックドアは後にCIAと中国の諜報機関の両方に利用されたと報告されている。影響：バックドアが義務化されれば、EU圏外のSignalやProtonなどのサービスがEU市場から撤退を選ぶ可能性が高く、EU市民が却ってより安全でないサービスを使うことになりかねない。
HNの反応と今後の見通し
HNで最多upvoteのコメント：「Chat ControlがEU議会で否決されたのは市民社会と技術者の粘り強いロビー活動の成果——今回も同様の対応が必要」。注目すべき動き：欧州データ保護委員会（EDPB）がすでに懸念を表明しており、EU司法裁判所（ECJ）もプライバシーと安全保障のバランスについての判例を積み重ねている。日本への影響：日本政府もサイバー犯罪条約（ブダペスト条約）の改定議論の中で類似の問題に直面しており、EU動向は国際的な先例になる可能性がある。

セキュリティ / Omarchy / Linux / 特権昇格 / DHH / root / 脆弱性開示 / 0xcc — OmarchyでAnyユーザーがrootに昇格できる脆弱性。333ポイント・326コメント。2026-08-31

Omarchyに
特権昇格の脆弱性——
任意ユーザープロセスが
root取得可能

0xcc.ioのセキュリティ研究者が「Omarchy: Any User Process Can Escalate to Root」と題したブログ記事を公開し、333ポイント・326コメントという本日2位の反響を呼んでいます。OmarchyはRails作者のDavid Heinemeier Hansson（DHH）が「自分のために作ったLinuxディストリビューション」として公開したArch Linuxベースのディストリビューションで、主に開発者向けにシンプルな設定済み環境を提供することを目的としています。 研究者はOmarchyのセットアップスクリプトまたは設定において、任意の非特権ユーザープロセスがroot権限を取得できる経路を発見しました。OmarchyがHNコミュニティ内でそれなりの利用者を獲得していたこともあり、この開示は大きな注目を集め、DHH本人もコメントに応答しました。
脆弱性の技術的詳細
Omarchyのセットアップ過程で作成される設定：特定のsudo設定またはpolkitルールが過度に許可的（overly permissive）な権限を付与していたと報告。攻撃経路：ローカルの非特権ユーザーが特定のコマンドシーケンスまたは環境変数操作を通じてroot shellを取得できる。影響範囲：Omarchyをインストールして使用している全てのマシン——特にマルチユーザー環境や共有開発サーバー。深刻度：CSSの「CRITICAL」相当——ローカル権限昇格（LPE）は物理アクセスまたは既存の低権限アクセスを持つ攻撃者がシステムを完全に掌握できるため。
DHHの反応と修正状況
HNのコメント欄でDHHが応答：「報告に感謝する。修正をリリースした」（概要）。コミュニティの指摘：「Omarchyはもともと『自分用』として作られ、セキュリティ監査を経ずに広く配布された——個人ツールを一般公開する際のリスク」。修正内容：問題のあるsudo/polkit設定を適切な権限に制限。アップデート方法：`omarchy-update`コマンドまたは手動でのパッチ適用が推奨されている。
教訓——「便利さとセキュリティのトレードオフ」
HNの議論から浮かんだ教訓：①「自分用ツール」を公開する場合は、自分が想定していない使われ方やセキュリティ前提が崩れるケースを考慮する必要がある。②Arch Linuxは高度な設定の自由度を持つが、その自由度はセキュリティリスクにもなり得る。③sudo・polkit・DBusの設定は「動けばOK」ではなく最小権限原則（Principle of Least Privilege）に従うべき。開発者が学べること：自分の開発環境スクリプトの`/etc/sudoers.d/`や`/etc/polkit-1/`の設定を今すぐ確認することを推奨するコメントが多かった。

Hy4の技術的特徴
Hy4の設計思想：KVMをベースにしつつ、Tencentのデータセンター規模のワークロードに最適化したVMM（Virtual Machine Monitor）。注目点：①Rustで実装されているとの報告——メモリ安全性をハイパーバイザーレベルで担保。②vhost-user・virtio等の標準インターフェースとの互換性を維持しつつ独自最適化。③コールドスタート時間の短縮——マイクロVM的なアプローチでコンテナとVMの中間的な起動速度を実現。AWSのFirecrackerとの比較：Firecrackerも同様のアプローチ（KVMベース・Rustで実装・最小限のデバイスエミュレーション）を取っており、HNでは両者の比較議論が活発に展開された。
オープンソース化の意図と懸念
Tencentがオープンソース化する理由：①外部開発者コミュニティによる改善・バグ修正の取り込み②採用企業の増加による実績作り③中国のクラウド技術の国際的な認知度向上。HNコミュニティの懸念：「Tencentはテンセント。中国の法律上、政府からの情報開示要求に応じる義務がある——ハイパーバイザーレベルのソフトウェアを本番環境で使用することへのリスクを慎重に評価すべき」という声が複数。一方で「コードはオープン——セキュリティ監査ができる。それが重要」という反論も。ライセンス：Apache 2.0で公開されており、商用利用・改変・再配布が自由。
開発者・インフラエンジニアへの意味
実用的な観点：①小規模クラウドプロバイダー・プライベートクラウド運営者が参照実装として利用できる。②「Rustで書かれたハイパーバイザー」の学習リソースとして有用——Rustでのシステムプログラミングの良い教材。③Firecrackerとの比較研究によってVMM設計のベストプラクティスが明確になる。HNコメント：「大手クラウドが内部で使っているものの設計を公開することで、業界全体の技術水準が上がる——GoogleのMapReduceやBigTableペーパーがHadoopを生んだように」。

セキュリティ / QubesOS / 任意コード実行 / copy-to-VM / バックチャネル / QSB-118 / 脆弱性 / CVE — QubesOSでcopy-to-VMエラー報告バックチャネル経由の任意コード実行。191ポイント・79コメント。2026-08-31

QubesOSで
任意コード実行——
copy-to-VMのエラー
報告バックチャネルが原因

QubesOS公式が「QSB-118: Arbitrary code execution in QubesOS via copy-to-VM error reporting backchannel」を公開し、191ポイント・79コメントを集めました。QubesOSはセキュリティを最優先に設計された「セキュリティ指向OS」で、異なる信頼レベルの作業を仮想マシン（Qube）で分離することで、一つの侵害が全体に波及しないよう設計されています。今回発見された脆弱性は、その設計の核となる「VM間のデータ転送機能」に関するものです。 copy-to-VM機能はファイルやクリップボードのデータを異なるQubeに転送するための仕組みですが、そのエラー報告メカニズムがバックチャネルとして機能し、悪意あるVMからAdmin Qube（または他のVM）に向けて任意コードを実行できる経路が存在したと報告されています。QubesOSの「信頼モデル全体への影響」という点で特に深刻とみなされています。
脆弱性の技術的メカニズム
copy-to-VM機能の仕組み：QubesOSのqrexec（Qubes RPC）フレームワークを通じてVMからVMにデータをコピーする際、転送先VMがエラーを返す場合の処理に問題があった。バックチャネルの形成：エラーメッセージの内容や構造が転送元VMから制御可能であり、それが転送先VM上でコマンドとして解釈される形式になっていた——いわゆる「コマンドインジェクション」の変形。信頼境界の侵害：QubesOSの設計では各VMは互いに隔離されているはずだが、この脆弱性により低信頼VMから高信頼VM（Work Qube・Admin Qube等）へのコード実行が可能になった。
影響範囲と深刻度
影響を受けるバージョン：QubesOS 4.xの複数バージョン（具体的なバージョン範囲はQSB-118に記載）。実際の攻撃シナリオ：①悪意あるWebサイトがブラウザVM（Untrusted Qube）を侵害する②攻撃者がcopy-to-VM機能を使ってWork Qubeやwork Qubeにファイルを「送ろうとする」③エラー報告バックチャネルを通じてWork Qubeで任意コードを実行する。QubesOSを「究極のセキュアOS」として使用しているジャーナリスト・活動家・研究者などの高リスクユーザーへの影響が特に懸念される。修正：パッチがリリース済みで即時適用が推奨。
HNの反応と設計への示唆
HNのコメントで最も議論されたポイント：「セキュリティが高まると攻撃の創造性も高まる——エラーメッセージをバックチャネルとして使う発想は単純だが、セキュリティモデルを設計した人間には盲点になりやすい」。Qubesチームの対応：公開時に修正を同時リリースし、Qubes Security Bulletin（QSB）として詳細な技術情報と緩和策を提供したことが高く評価された。設計論：「エラーパスはセキュリティ設計の盲点になりやすい——正常系の信頼境界は厳密に設計されても、例外処理は甘くなりがち」という教訓は汎用アプリケーション開発にも直接適用できる。
