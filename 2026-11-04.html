Postmanが無断で
AIプラグインを
自動インストール
——全APIデータを外部送信——868pt

「Postman silently auto-installs AI plugins and attempts to share all API data」がHNで868ポイント・284コメントを集めています。開発者のsidgarimella氏がGitHubのissueで報告した問題で、PostmanがユーザーへのCI/CDなしに独自のAIプラグインをサイレントインストールし、ユーザーのAPIリクエスト・レスポンス・認証情報を含む全データをPostmanのサーバーに送信しようとしていることが発覚しました。開発者ツールにおける信頼と透明性の問題として、HNで強い反応を引き起こしています。
何が起きているか——具体的な問題
無断インストール＋全APIデータの外部送信
報告された問題: (1) Postman 11.xへのアップデート後、ユーザーが気づかないうちに「Postman AI」プラグインが自動インストールされる。(2) プラグインは起動時にAPIコレクション・リクエスト履歴・環境変数（APIキー・パスワードを含む）をPostmanのAI基盤に送信しようとする。(3) オプトアウト設定はあるが、デフォルトはオプトイン——アップデートの注記には小さな文字でのみ記載。(4) エンタープライズプランでは設定でオフにできるが、個人・チームプランでは制限が薄い。影響範囲: Postmanは全世界で3,000万人以上の開発者が使用する最大手のAPIテストツール——医療・金融・インフラ開発者を含む。セキュリティへの影響: 「開発環境のAPIキーがPostmanのAIサーバーに送信されるということは、Postmanが漏洩した場合に攻撃者が大量の実環境APIキーを入手できる」。
HNの284コメント——移行先とリアクション
「Insomniaへ移行」「Bruno一択」という声が殺到
コミュニティの反応: 「これはPostmanの終わりの始まり——信頼を失ったツールは開発者には使えない」という声が多数。推奨代替ツール: (1) Bruno: オープンソースのAPIテストツール——コレクションをGitで管理できるローカルファーストな設計。外部サーバーに一切データを送らない。(2) Insomnia: Kong社が開発するオープンソースのPostman代替——クラウド機能はオプトイン。(3) HTTPie: シンプルなCLIベースツール——クラウド不要。(4) VS Code REST Client: 拡張機能でリクエストを.httpファイルとして管理——GitリポジトリにAPIテストを含められる。actionable: 今すぐPostmanの設定→Privacy→「Allow Postman to use my API requests for AI training」をオフにするか、Brunoへの移行を検討する。
なぜこれが重要か——開発ツールの信頼崩壊
「ツールが武器になる」時代の警鐘
背景: PostmanはAdvent VC主導で2021年に$5.6Bの評価を受けたユニコーン企業——投資家への回収圧力がAI機能のマネタイズに向かわせているという見方がある。開発ツール業界の問題構造: 「無料→SaaSモデル→AIデータ収集」というパターンがPostmanだけでなく複数のDevToolsで顕在化している——開発者のAPIキーやコードという極めてセンシティブなデータが狙われている。コンプライアンス上の問題: 多くの企業では「認証情報を外部サービスに送信してはいけない」というセキュリティポリシーがある——Postmanのデフォルト設定はこのポリシーに違反する可能性がある。Claude Codeとの関連: MCP(Model Context Protocol)を通じてAPIクライアントとAIが連携する方向が進んでいる中、開発ツールのデータプライバシーは今後ますます重要な問題になる。

AI / LLM / DeepMind / Qwen / ファクトチェック — 2026-11-04

「AstraがQwenの
ウェイトを改善」は
誇大だった
——honnibal.devが事実確認——844pt

「The 'Astra can read and write weights to improve Qwen' post is misleading」がHNで844ポイント・187コメントを集めています。spaCyの開発者として知られるMatt Honnibal（@syllogism）が、前日にHNで大バズりした「AstraがQwenのウェイトを直接書き換えて改善できる」という主張を詳細に検証。実際に何が行われていたかを技術的に解説し、AI研究の報道における「印象操作」の問題を指摘した記事です。
元の主張と実際の内容の違い
誇大に聞こえた主張: 「DeepMindのAstraがQwen-2.5のウェイトを読み書きして能力を改善できる——AIがAIを自律的に改善するウェイト空間プログラミングの実証」。Honnibalの事実確認: (1) 「ウェイトの読み書き」の実態は、Astraが少数のパラメータを手動で指定した非常に狭い範囲で微調整しただけ——「AGI的な自己改善」とは程遠い。(2) ベンチマーク改善の「約12%」は、特定の数学タスクのサブセットのみ——汎用的な改善ではない。(3) 実験コードを読むと、Astraはどのウェイトを変えるかを推論しているのではなく、人間が指定したパラメータ範囲内で勾配降下法に近い方法を実行しているだけ。(4) 「これは基本的にプログラマブルなファインチューニングの別表現であり、革命的な新技術ではない」。
なぜこういう誇大報道が起きるのか
Honnibalの分析: 「AI研究の発表タイトルや要約は、印象的に聞こえるよう意図的に構成されることが増えている——査読前のプレプリント文化と組み合わさると、技術的に不正確だが「すごそうな」内容がSNSで爆発的に広がる」。読者側の問題: 「HNのような技術者コミュニティでさえ、タイトルだけで大量のポイントが集まることがある——論文の実装詳細を読んだ人は少数だった」。HNコミュニティの反応: 「これを指摘してくれてありがとう——昨日の議論で懐疑的なコメントをしたら批判されたが、今日Honnibalが詳しく検証してくれた」「AI研究のファクトチェック文化が必要」。今後への教訓: 「『AIがAIを改善した』という見出しには、実装詳細を必ず確認する習慣が必要——こういった誇張は業界全体への信頼を損なう」。
Actionable——AI研究を正しく読む技術
Honnibalが推奨する読み方: (1) 「実装コードを読む」——論文やブログの要約でなくコードそのものを見ると何をやっているかが明確になる。(2) 「ベンチマークの範囲を確認する」——「タスクXで改善」がどの程度の汎用性を持つかを確かめる。(3) 「実験設定のベースラインを確認する」——比較対象が弱い場合、改善幅は大きく見えがち。(4) 「作者のインセンティブを考える」——資金調達中のスタートアップと大学研究者では発表のインセンティブが異なる。ツール: Semantic Scholar・Papers With Code・connected paperなどで論文の引用・再現状況を確認できる。誇大報道に対抗するコミュニティ: LessWrong・Alignment Forum・Alex Tamkin氏のAI Sagaなどが技術的に正確なAI研究解説を提供している。

「Jailbreaking my car's navigation system just so I can change the time」がHNで530ポイント・210コメントを集めています。エストニアのエンジニアxx_ns氏が、自分のRenault車の純正カーナビシステムを数週間かけてリバースエンジニアリングし、時刻設定のロックを解除するまでの全過程を詳述したブログ記事です。なぜそこまで——という問いへの答えが「夏時間に対応していないからイライラしたから」という点も含め、エンジニアの心理をよく捉えたユーモラスな記録です。
ハックの全工程——何をどうやったか
問題の発端: Renaultの純正ナビ（MediaNav Evolution）はGPS信号から自動的に時刻を取得するが、エストニアの夏時間（EET/EEST）への対応が壊れており、常に1時間ずれた時刻を表示していた。メーカーサポートの対応: 「これは仕様です。ファームウェアアップデートで修正を検討します」→3年経っても修正なし。ハックの手順: (1) OBD-IIポートからシステムのUARTコンソールへのアクセスを発見。(2) ファームウェアをシリアル接続で抽出してbinwalkで解析。(3) Linux ELFバイナリとして実行されているナビアプリのリバースエンジニアリング。(4) 時刻同期ロジックを担当しているC関数を特定。(5) ARM向けのパッチバイナリを作成してシステムに書き込み。結果: 「念願の正しい時刻が表示されるようになった。所要時間: 約4週間」。
HNの210コメント——「修理権」の権利運動
最多コメントのスレッド: 「修理する権利（Right to Repair）の完璧な事例——自分が買った製品を自分で修正できないのはおかしい」という議論に発展。欧州の法的背景: EUでは2024年に修理権指令（Right to Repair Directive）が成立——メーカーは製品の修理に必要な情報・部品・ソフトウェアを合理的な価格で提供することが義務付けられた。日本の状況: 「日本では修理権の法整備が遅れているが、2025年に経産省が検討を開始した」というコメントも。技術的な興味: 「OBD-IIポートからUARTコンソールへのアクセスという発想が面白い——汎用車診断ポートが実は強力なデバッグ入口になっている」。類似事例: 「古いBMWのiDriveをハックした話」「ToyotaのEntune APIを解析した話」が次々とリンクされた。
Actionable——自分でも試してみたい人へ
入門リソース: (1) car-hacking.orgの「Car Hacker's Handbook」——OBD-IIプロトコルからCANバスのリバースエンジニアリングまで体系的に学べる無料書籍。(2) OpenGaragesコミュニティ——車載システムのハックを共有するオープンコミュニティ。(3) CANtoolsライブラリ（Python）——CANバスのデータをデコードするためのPythonライブラリ。注意事項: 「ECU（エンジン制御ユニット）への書き込みは安全上のリスクがある——ナビ系の独立したシステムのみを対象にすること」「車のコンピュータへの不正アクセスは国・地域によっては違法になる場合がある——自己責任で」。最初のステップ: 中古OBD-IIアダプター（\$10〜\$30）とTorqueアプリで自分の車の基本データを読むことから始められる。

チェス / アルゴリズム / コンピューターサイエンス / 歴史的思考実験 — 2026-11-04

現代チェスエンジンを
Pentiumで動かせば
1996年のカスパロフに
勝てるか？

「Could a modern chess engine on a Pentium have defeated Kasparov in 1996?」がHNで414ポイント・189コメントを集めています。セキュリティ研究者のNicholas Carliniが書いた思考実験記事で、1996年当時のハードウェア（Pentium Pro 200MHz）に現代のチェスエンジン（Stockfish 17やLeela Chess Zero）を移植して動かした場合、どの程度の強さになるかを実際にベンチマークしながら計算した内容です。「アルゴリズムの改善」と「ハードウェアの改善」のどちらがより大きく貢献したかを明らかにする実験として注目を集めています。
実験の結果——アルゴリズム vs ハードウェア
背景: 1996年のDeep Blue vs Kasparovマッチ——IBM製の専用チェスハードウェアとカスタムチップが毎秒2億手を計算してカスパロフに最初の公式対局で1勝した歴史的事件。Carliniの実験: 現代のStockfish 17を「Pentium Pro相当の計算速度（約100万ノード/秒）」に制限してシミュレーション。現代Stockfishの計算効率: 同じノード数で計算した場合、Stockfish 17は1996年のDeep Blueより推定2000Eloポイント以上強い。理由: (1) アルファ・ベータ法の改良（MCTS・移動順序最適化）で無駄な探索を大幅削減。(2) 評価関数のニューラルネット化（NNUE）で局面評価の精度が劇的向上。(3) 並列化アルゴリズムの改善で複数コアを効率的に活用。結論: 「Pentiumで動かした現代Stockfishは、1996年当時のカスパロフを高確率で倒せる——アルゴリズムの改善が40年で1000Elo以上に相当することを示している」。
HNの189コメント——AI全般への示唆
最も評価されたコメント: 「これはチェスだけでなく、ML全体に言えること——GPT-4レベルの能力をGPT-2時代のGPUで実現できるアルゴリズムが既にある可能性が高い。コンピューティングコストよりアルゴリズムのブレークスルーが先に来る」。量子コンピューティングとの比較: 「量子コンピュータのハードウェア改善を待つよりも、古典コンピュータ上のアルゴリズム改善の方が実用的な意味でずっと速く進歩している」。類似研究: 「Chess Algorithmic Progressという2024年の論文でも同様の結論——1990年代から現在までチェスエンジンはほぼ毎年30Eloずつ向上、ハードウェアは同期間に約15Elo相当の貢献」。日本のコメント: 「将棋ソフト（YaneuraOuなど）でも同様の分析があり、2010年代中盤には既にプロを超えていたが、当時のハードウェアを当時のアルゴリズムで動かした場合はプロに及ばなかった」。

AI / LLM / Qwen / ローカルAI / モデル解釈可能性 — 2026-11-04

ラップトップの
Qwen 27Bが
モデルウェイトを
解釈できる——400pt

「Qwen 3.8 27B on my laptop can interpret model weights, too」がHNで400ポイント・135コメントを集めています。Simon Willison氏がblog.simonwillison.netで公開した実験記事で、MacBook Pro（M4 Max）でOllama経由でローカル実行しているQwen 3.8 27Bモデルが、別のLLMのウェイトを読み込んで「このウェイトパターンが何を表現しているか」を解釈できることを実証した内容です。ローカルで動くモデルでもウェイト解釈能力を持てることへの驚きと、その実用的含意を考察しています。
実験の内容——何ができて何ができないか
実験の設定: Simon氏がQwen 3.8 27B（4bit量子化、約16GBのVRAM消費）をM4 MaxのMacBook Proでローカル実行。llama.cppのツールを通じて、小型のモデル（GPT-2 Small相当）のウェイトテンソルをCSVとしてエクスポートしてQwenに渡した。できたこと: (1) 埋め込み層の特定次元が「地名」「感情表現」などの意味的クラスターに対応している傾向を正しく推論。(2) アテンションヘッドの重みパターンから「このヘッドは主語・動詞の依存関係に敏感」という推論を生成。(3) 「このモデルは英語テキストで学習されている」「語彙サイズから約50K tokenの辞書を使っている」という推論も正確。できなかったこと: 大規模モデル（70B+）のウェイトを直接解釈することはメモリ制約から不可能。個々の「ニューロン」が何を表現しているかを精密に特定するには専用の解釈可能性ツールが必要。
なぜこれが面白いのか——モデル解釈可能性の民主化
解釈可能性研究の現状: LLMの内部表現を人間が理解できる概念にマッピングする「モデル解釈可能性（Interpretability）」研究は、Anthropic・DeepMind・EleutherAIなどが先端を走る研究分野——従来は大規模な計算資源が必要とされていた。ローカルモデルでの実現の意義: 「27Bのモデルが解釈可能性タスクを小型モデルに対して実行できるなら、研究者・開発者が手元の環境で自分のモデルを理解するためのツールとして使える」。Claude Codeとの関連: Anthropicが開発している「Mechanistic Interpretability」研究——モデルが特定の推論をする際にどの回路が活性化するかを理解する——とローカルQwenの実験は同じ方向性を向いている。将来の展望: 「ファインチューニングしたモデルがどこで元のベースモデルから乖離したかを理解したり、安全性上問題のある内部表現を特定したりするためのローカルツールが生まれる可能性」。

Vesuvius Challenge——世界が注目するプロジェクト
背景: ヘルクラネウム写本は79年のヴェスヴィオ火山噴火で炭化した約1,800本の巻物——物理的に開こうとすると粉砕するため、2,000年間内容が不明なまま。2023年のブレークスルー: Vesuvius Challengeが設定した$1,000,000の賞金と、機械学習・X線マイクロCT技術の組み合わせにより、2023年末に最初の文章解読に成功。現在の進捗: PHerc. 306Bは今年初めて高解像度スキャンが完了——今回の報告はその初期解析結果。解読された内容: まだ断片的だが、ギリシャ語の哲学的テキストの一部と推定されるフレーズが確認されている。意義: 「これはまだ全体の1%にも満たない——これが完全に解読されると、プラトンやアリストテレスの時代の失われた著作が復元できる可能性がある」。
