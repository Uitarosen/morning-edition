Navier-Stokes
問題が解決——

クレイ数学研究所が「Navier-Stokes方程式の存在と滑らかさ」問題の解決を正式に発表しました。298ポイント・240コメント。7つのミレニアム問題のうち、これまでに解かれたのはポアンカレ予想（2003年）のみ。それ以来初の解決となる歴史的な発表で、流体力学・気象予測・航空宇宙工学への影響は計り知れません。
何が「解かれた」のか
Navier-Stokes方程式は流体（水・空気・血液など）の運動を記述する偏微分方程式。「任意の初期条件で、時間が経っても解が滑らかに存在し続けるか、それとも有限時間内に特異点（無限大）が生じるか」という問いが100年以上未解決だった。今回の証明は「全3次元空間で解は永遠に滑らか」という主張を証明したとされる。
HNの反応——懐疑論も
HNでは「クレイ研究所の公式発表なので信頼できる」という声と、「査読プロセスの詳細は？」という慎重論が拮抗。数学者がコメントし「証明のアーカイブを今夜読む」という投稿が多い。過去にもNavier-Stokes「解決」を主張した論文が後に誤りと判明した例があるため、コミュニティは興奮しながらも慎重な姿勢。
実用上の意味
直接的な計算アルゴリズムへの応用は数十年先かもしれないが、数値シミュレーションの理論的基盤が固まる。気候モデリング・乱流の予測・新型航空機の設計などで「なぜシミュレーションが正確なのか」の根拠が強化される。$100万ドルのクレイ賞が授与される予定。

セキュリティ / Android / VPN / NAT-T / プライバシー / カーネル — 161ポイント・42コメント。2026-09-13

AndroidのVPN
「ロックダウン」を
NAT-Tが
突き破る

AndroidのVPN「ロックダウンモード」（VPN接続なしでは一切の通信を遮断する設定）が、NAT-T（NAT Traversal）キープアライブパケットによってバイパスされるという脆弱性が報告されました。161ポイント・42コメント。VPNを使っている高リスクユーザー（ジャーナリスト・活動家・プライバシー重視のユーザー）にとって重大な発見です。
技術的な仕組み
NAT-Tキープアライブは、NAT機器との接続を維持するためにVPNトンネルの外側でUDPパケットを定期送信する機能。Android実装では、VPNロックダウンが有効でも、この特定のパケットだけがVPNトンネルを通らずに直接インターネットに送出されていた。送信間隔やIPアドレス情報が漏れる可能性がある。
誰がリスクを負うか
「ロックダウンモード」を明示的に有効にしているユーザーは、セキュリティ要件が高い（検閲地域のユーザー、内部告発者、セキュリティ研究者など）。このモードを使っていない一般ユーザーには影響なし。研究者は「Androidの普及とVPN利用増加を考えると、影響範囲は小さくない」と指摘。
対策と現状
Googleへの脆弱性報告は既に行われている。現時点での回避策として、研究者は「影響を受けるIPsec/IKEv2 VPNを避け、WireGuardを使う」ことを推奨。GrapheneOSはこの修正をすでに実装済みとされ、プライバシー重視ユーザーへの乗り換え理由が増えた形。

Linux版Zoomが
X11クリップボードを
ユーザーの
知らぬ間に読んでいた

Simon Tathamが「Linux版ZoomクライアントがX11クリップボードに書き込まれた内容を能動的に読み取っている」とMastodonで報告し、HNで86ポイント・27コメントを集めました。PuTTYの開発者として著名なTathamの指摘は信頼性が高く、コピーしたパスワードや機密文書がZoom会議中に読み取られる可能性があります。
何が問題なのか
X11のクリップボードモデルは「所有者がいる間だけ内容を保持し、他のアプリが明示的に要求した時のみ提供する」設計。しかしZoomはクリップボード所有者を変更せずに、バックグラウンドで定期的にクリップボードの内容をポーリング（能動的に取得）していた。ユーザーがコピーした内容が会議中にZoomサーバーへ送信される可能性を否定できない。
Zoom側の機能的意図
おそらくZoomの「クリップボードを共有」機能のための実装と推測されるが、ユーザーが明示的にクリップボード共有を有効にしていない状態でも動作していた点が問題。「機能のためにアクセスが必要」は理由になるが、「常時監視」は過剰。HN: 「良い意図でも、設計が悪い実装」という評価が多い。
今すぐできる対策
①Wayland（次世代Linuxディスプレイシステム）はX11と異なりアプリ間のクリップボード盗み見を設計上防ぐ——UbuntuやFedoraの最新版はデフォルトがWayland。②会議中に機密情報をコピーしない。③Zoomをサンドボックス（Flatpakなど）で実行しクリップボードアクセスを制限する。

Rust / 型システム / プログラミング言語 / 安定化 / Never型 / コンパイラ — 96ポイント・12コメント。2026-09-13

RustのNever型が
ついに安定化へ——
5年越しの
型システム決着

Rustの型システムで長年議論されてきた「Never型（`!`）」の完全安定化が進んでいるという記事がHNで96ポイント・12コメントを集めました。`!`型は「この式は決して値を返さない」ことを型として表現するもので、エラー処理・制御フロー・型推論において重要な役割を持ちますが、完全な安定化には多くの複雑な設計問題がありました。
Never型とは何か
関数 `fn diverges() -> !` は「この関数は絶対に戻らない（パニック、無限ループ、プロセス終了など）」を型で表現する。`!`型はすべての型のサブタイプ（bottom type）として機能するため、`match`アームや`if`式でどんな型とも一致できる。これにより型推論が大幅にシンプルになる。
なぜ5年かかったのか
問題は`!`をtraitの実装対象として安定化する際に生じる。例えば`impl From for T`は「Neverから任意の型への変換」を表すが、これが既存のtraitシステムと微妙な相互作用を起こす。コヒーレンスルール（孤立した実装の禁止）との整合性が技術的難題だった。今回の解決策はRFC 3672として文書化。
実用上の変化
安定化後は`Result`（エラーが決して起きないResult）や`!`を型パラメータとして使ったジェネリクスが書きやすくなる。`Infallible`型（現在の代替）を使った回避策が不要になる。「型で不可能性を表現する」Rustの哲学が一段と完成に近づく。

AI / ベンチマーク / コーディング / 評価 / エンタープライズ / SWE-bench — 34ポイント・26コメント。2026-09-13

Real-SWE——
非公開の実企業
コードで
AIをベンチマーク

公開されているベンチマーク（SWE-benchなど）ではなく、実際の非公開エンタープライズコードベースでAIモデルの性能を評価する「Real-SWE」がHNで34ポイント・26コメントを集めました。訓練データへの混入が不可能な非公開コードで評価することで、AI開発ツールの実際の有用性を正確に計測しようという取り組みです。
なぜ既存ベンチマークが不十分か
SWE-benchはGitHubの公開リポジトリ（django、scikit-learnなど）のissueを使用しているため、AIモデルの訓練データに含まれている可能性が高い。Real-SWEは参加企業の非公開コードを使用し、解答が訓練データに存在しないことを保証する。HN: 「これが真の意味での能力評価だ」という賛同が多い。
結果の概要
公開ベンチマーク上位のモデルが必ずしも実企業コードで上位にならない、という乖離が確認された。特に「巨大なレガシーコードベース」「社内独自フレームワーク」「不完全なドキュメント」という実際の開発環境で、モデル間の差が大きく開く傾向があった。詳細スコアは参加モデルの同意のもとで公開。
実際に使うAIツールを選ぶ参考に
開発チームがAIコーディングツールを選ぶ際、公開ベンチマークだけで判断するのは危険。Real-SWEのようなプライベートコードでの評価、または自社コードでの小規模POCを必ず行うこと。HN: 「AIツール評価の標準がPublic → Privateへシフトする転換点になる可能性がある」。
