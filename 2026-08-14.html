ハードウェア / セキュリティ / DRAM / メモリ攻撃 / Rowhammer / GitHub / エクスプロイト / 変わった科学 — DRAMを物理的に「スパゲッティ化」するメモリ攻撃手法の概念実証がGitHubで公開。442ポイント・130コメント。2026-08-13

DRAMを
「スパゲッティ化」する
メモリ攻撃——
新手法がGitHubに

セキュリティ研究者matt_dが「Spaghettifying DRAM」と題した概念実証コードをGitHubで公開し、HNで442ポイント・130コメントを集めました。タイトルの「スパゲッティ化」は物理学用語（ブラックホールに落ちる物体が引き伸ばされる現象）から借りた命名で、DRAMの特定行を繰り返しアクセスすることで隣接行にビットフリップを引き起こす「Rowhammer」攻撃の新しい亜種実装です。 従来のRowhammer攻撃に対して多くのDIMM・CPU・OSレベルの緩和策が実装されてきましたが、この実装は複数の緩和策を組み合わせて回避するアプローチを取っており、特定の構成ではまだ有効であることを示しています。リポジトリ名の「skitter-creek-bath-salts」というユーモラスな名前もHNで話題になりました。HNでは「Rowhammerは2014年から知られているが、2026年になっても完全な解決策がないのは設計上の根本的な問題がある」「DDR5のオンダイECC（OEC）がこれに対してどこまで有効かが焦点」「GitHubがPoCコードを削除するかどうか——公開の是非の議論も」という130コメントが展開されました。
Rowhammer攻撃とは
DRAMの物理的特性（隣接セル間の電荷漏れ）を利用した攻撃。特定のメモリ行を高頻度でアクセスすると隣接行のビットが反転する現象（ビットフリップ）を意図的に誘発する。特権昇格・カーネル権限取得・仮想マシン脱出など深刻な権限昇格に悪用された実績がある。2014年のGoogle Project Zero発見以来、多くの緩和策が実装されたが根本解決には至っていない。
スパゲッティ化手法の新規性
既存のRowhammer緩和策（Target Row Refresh=TRR、pTRR、Blast Radius制限）を複数の角度から同時に回避するパターンを組み合わせた実装。特定の商用DIMMs構成でビットフリップを誘発することに成功。DDR4世代の特定チップでは依然として有効であることを実証。DDR5のオンダイECCは多くのケースで有効だが、エラー率の高い構成では補正能力を超える場合がある。
対策の現状
DDR5への移行がRowhammer対策として最も効果的——ただし全てのDDR5 DIMMが同等の保護を持つわけではない。ECC（Error-Correcting Code）メモリを使うことでビットフリップの多くを補正・検出可能。OSレベルの緩和策（Linuxの/proc/sys/vm/page_isolation設定等）は完全ではない。クラウド環境では仮想化のレイヤーがある程度の保護を提供するが、共有物理メモリが攻撃対象になり得る。

「退屈な技術を
選べ」——
11年後も刺さる

イノベーション・トークンとは
McKinley氏が提唱した概念：チームが保有する「新しいことを試す体力」は有限。新技術の採用には学習コスト・デバッグコスト・採用コスト・オペレーションコストが伴う。これらを「トークン」として考えると、どの問題に新技術を投資するかの選択が明確になる。全ての問題に最新技術を使おうとするチームは、最も重要な問題への投資余力がなくなる。
2026年のAI時代における読み方
「AIをどのプロジェクトに投入するか」という選択がイノベーション・トークンの典型的な現代版。全ての機能にLLMを使おうとするのは「最新技術信仰」と同じ過ちに陥る可能性がある。「このタスクはルールベースで十分か、LLMが本当に必要か」という問いを常に持つことが、AIプロジェクトの失敗を避ける第一歩。退屈なAI（最も広く使われている・サポートが充実している・動作が予測可能なモデル）を選ぶことにも同じ原則が適用できる。
退屈な技術リスト（2026年版）
データベース：PostgreSQL（依然として最良のデフォルト）。キャッシュ：Redis。キュー：PostgreSQLのSKIP LOCKED、または充分に使われてきたRabbitMQ/SQS。Webサーバー：nginx/caddy。言語：Python/Go/TypeScript（用途による）。LLMインフラ：最も実績のあるAnthropicまたはOpenAIのAPI——独自モデルの自前ファインチューニングはトークンを大量消費する高リスク選択。

Litt氏の定義：ユーザーが本当に抱えている問題を正確に特定する力。AIに投げる前に「何を解くべきか」を定式化する力。AIの出力が正しい方向を向いているかを評価する力。システム全体がどう機能するかをメンタルモデルとして持つ力。「コードを書く」という行為が自動化されても、これらの能力は代替されない——という主張。これは従来の「シニアエンジニアとジュニアエンジニアの差」にも通じる概念。

組織・チームへの含意
