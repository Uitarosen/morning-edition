Claude Code、
プロンプト読む前
に33kトークン
消費——4.7倍の差

Systima.aiが「Claude Code sends 33k tokens before reading the prompt; OpenCode sends 7k（Claude Codeはプロンプトを読む前に33kトークンを送信、OpenCodeは7k）」を公開し、348ポイント・196コメントという活発な議論を呼んでいます。 記事の核心は「イニシャライゼーションオーバーヘッド」の問題です。Claude Codeはセッション開始時に、ユーザーのプロンプトを処理する前に、システムプロンプト・コードコンテキスト・ツール定義などで約33,000トークンをAnthropicのAPIに送信します。一方、オープンソースの代替ツールであるOpenCodeは同様の初期化をわずか7,000トークンで行います。この差4.7倍が毎回のコーディングセッションで積み重なります。 HN上では「プロンプトキャッシュが有効な場合、33kの繰り返し送信は最小コスト——でも最初の1回目と新規プロジェクトではキャッシュミスで全額課金される」「OpenCodeがなぜ少ないかは重要——ツール定義を削ぎ落とした軽量設計か、それとも機能を犠牲にしているのか」「Claude Codeはこの「重さ」の代わりにコンテキスト理解力と自律修正能力を持っている——単純な比較では見えないトレードオフ」という196コメントが展開しています。
Claude Code
~33,000 トークン
プロンプト読み込み前のオーバーヘッド。システムプロンプト・ツール定義・コンテキスト初期化を含む。Anthropic APIへの送信コストが毎セッションかかる
OpenCode
~7,000 トークン
同等の初期化を7kで完了。オープンソース・軽量設計。Claude Codeの約4.7倍の効率。ただし機能セットの差には注意が必要
プロンプトキャッシュの影響
繰り返しは安い
Anthropicのキャッシュ価格：通常の10%。同一セッション内の繰り返しはほぼ無料。ただしキャッシュミス（新規プロジェクト・長時間後）は全額課金。1日あたりの実コストはキャッシュヒット率に依存
実際のコスト感
月額への影響
ヘビーユーザー（1日50セッション想定）：キャッシュなし換算で月数十ドルの差になりうる。Claude Code Pro（$100/月）契約ならAPIコスト分離のため影響なし。API直接利用ユーザーは要注意

AI / コーディングエージェント / 数学 / テレンス・タオ — フィールズ賞数学者テレンス・タオが「モダンなコーディングエージェントで古いアプリと新しいアプリを作る」体験記を公開。プロ以外のプログラマーがAIエージェントで何を実現したか。386ポイント・110コメント

テレンス・タオ
が語る——
コーディング
エージェント体験

フィールズ賞受賞数学者のテレンス・タオ（Terence Tao）がWordPressブログに「Old and new apps, via modern coding agents（モダンなコーディングエージェントを通じた古いアプリと新しいアプリ）」を投稿し、386ポイント・110コメントを集めました。タオは自身が「プロのプログラマーではない」と断りながら、コーディングエージェントを使って自分の研究・教育ツールとして使っていた古いウェブアプリを復活させ、さらに新しいツールを作った体験を詳述しています。 特に印象的なのは、タオが「数十年前に書いてそのまま放置されていたJavaScriptアプリ」をコーディングエージェントに渡し、現代のブラウザで動くように修正してもらっただけでなく、機能追加まで行った点です。タオは「コードを一行も書かずにこれができた」と語り、数学の視覚化ツールや計算補助ツールを自分のニーズに合わせて整備できたことに率直な驚きを表明しています。 HN上では「世界最高の数学者がAIコーディングに感動している事実は、AIツールの成熟度を示す強いシグナル」「タオのような人が自分でアプリを整備できるようになると、数学教育の可能性が広がる——彼が作ったビジュアライゼーションツールが公開されればインパクト大」「プロでないユーザーのコーディングエージェント体験記として読むと、ハルシネーションへの対処法や反復改善の実態が分かる」という110コメントが展開しています。
タオが使ったユースケース
古いアプリの復活：数十年前に書いたJavaScriptベースの数学ツールを現代のブラウザ向けに修正。新規アプリの作成：研究・教育目的の計算・可視化ツールをゼロから制作。特徴：コードを一行も手書きせず、エージェントへの自然言語指示のみで完成。タオの評価：「ツールのロジックを設計し、エージェントに実装させる分業が機能した」——エージェントの限界についても率直に言及
プロでないプログラマーにとっての意味
タオのポジション：数学は一流だがコーディングはアマチュアレベル。重要な示唆：「ドメイン知識がある人がコーディングエージェントを使うと、エージェントが最も強力に機能する」——何を作りたいかを正確に言語化できるからこそ、AIの出力を評価・修正できる。逆の課題：ドメイン知識なしにコーディングエージェントを使うと、出力の正しさを検証できない。タオは数学の正確さでエージェントの出力を評価できた
既存コードのリバイバルというユースケース
注目すべき点：「古いコードをモダン化する」はコーディングエージェントの最も強力なユースケースの1つ。理由：旧APIを新APIに置き換える・非推奨関数を更新する・ブラウザ互換性を修正するは、エージェントが得意な反復パターン認識タスク。実際の効果：20年前のDOM操作コードをモダンなJSに変換・古いXMLHttpRequestをfetch APIに置き換えなどが指示なしに自動実行される事例が報告されている。タオの体験はこれを一流研究者が追体験した証言

AI / LLM / geohot / 批評 / ハイプ — George Hotz（geohot）が「LLMは好き、ハイプは嫌い」を投稿。技術そのものへの評価とAI業界を覆うバズワードと過剰期待への批判を分離して語る。248ポイント・136コメント

geohot——
「LLMは好き、
ハイプは
嫌いだ」

tinyboxやcomma.aiで知られるGeorge Hotz（geohot）が自身のブログに「I love LLMs, I hate hype（LLMは好き、ハイプは嫌い）」を投稿し、248ポイント・136コメントを集めました。記事はLLMという技術そのものへの率直な賞賛と、それを取り巻く業界のハイプ・誇張・バズワードへの鋭い批判を明確に分けて論じています。 geohot氏がLLMを「好き」な理由として挙げるのは、コーディング補助・数学的推論・知識検索における実際の有用性です。「ChatGPTは毎日使う。Claude Codeは毎日使う。これらは本当に役に立つ」と明言しています。一方で「嫌い」な側面として、「AGIが来年来る」「AIが全ての仕事を奪う」「意識が生まれた」といった誇大言説や、VC・メディア・AI企業自身が作り出すハイプサイクルへの不満を明示しています。 HN上では「geohot は技術と言説を分けて評価している——これは正しいアプローチ。LLMは便利なツールだが神秘的な存在ではない」「geohot の批判の対象はOpenAIのSam Altmanが体現するような過剰なビジョン言説だろう——それと技術の価値を切り分けるのは重要」「矛盾して聞こえるが、LLMの最もよい使い方を知っている人間がハイプに最も批判的——熟練ユーザーほど現実的」という136コメントが展開しています。
geohot が「好き」なLLMの側面
毎日使うツールとしての実用性：コーディング補助（Claude Code）・検索の代替・ドキュメント要約・コードデバッグ。賞賛ポイント：「知識の民主化ツールとして機能している——専門家への質問が誰でもできる」。技術的な評価：トランスフォーマーアーキテクチャの優雅さ・スケール則の発見・RLHF等の技術革新は本物の科学的成果。geohot 自身がcomma.aiでLLMを使った自動運転開発を行っていることからも、技術への信頼は本物
geohot が「嫌い」なハイプの側面
具体的な批判対象：①「AGI は1〜2年以内」という根拠なき予測を繰り返すCEOや投資家②「AIが全ての知的労働を奪う」という過剰な脅威言説③「モデルに意識が宿った」という技術的根拠ゼロの主張④数十億ドルの評価額を正当化するための誇大マーケティング。背景：AI企業がVC資金を調達するためにハイプを維持するインセンティブがある——これが技術への正確な評価を歪める。geohot の立場：商業的インセンティブのない独立した批評者として発言
「技術 vs 言説」を分ける思考法
geohot 流のフレームワーク：「今日役に立つか」と「誇大な未来予測」を切り分ける。実践的な問い：この技術は今すぐ自分の仕事を改善するか？→YesならLLMは使う価値がある。これは10年後に世界を変えるか？→分からない、そして気にする必要はない。歴史的文脈：クラウドコンピューティング・スマートフォン・ブロックチェーンにも同様のハイプサイクルがあった。残ったのは実用的な技術だけ。LLMからも実用性は残る——ハイプが剥がれた後に何が残るかを見ている段階

開発ツール / Emacs / ターミナル / libghostty / Ghostty — Ghosttyターミナルのコアライブラリlibghosttyを使ったEmacs用ターミナルエミュレータ「Ghostel.el」が公開。Emacsユーザー向けの新しい選択肢。254ポイント・47コメント

Ghostel.el——
libghostty で
動く Emacs 用
ターミナル

「Ghostel.el: Terminal emulator powered by libghostty」がHNで254ポイント・47コメントを集めました。Ghostel.elはEmacs内で動作するターミナルエミュレータで、Mitchell Hashimoto（HashiCorp創業者）が開発した高速ターミナルアプリ「Ghostty」のコアライブラリであるlibghosttyを利用しています。 Ghosttyはその高速レンダリングとmacOS・Linux向けのネイティブ統合で2024年末に大きな注目を集めたターミナルアプリです。libghosttyはそのレンダリング・VT100/xterm互換性処理・フォントシェーピングなどのコア機能をライブラリとして切り出したものです。Ghostel.elはこのlibghosttyをEmacsのモジュールシステム経由で呼び出し、Emacs内に組み込まれたターミナルとして動作させます。既存のEmacsターミナル（term.el・vterm）と比較して、libghosttyのVT互換性の高さとレンダリング速度が利点として挙げられています。 HN上では「vtermを長年使ってきたが、Ghosttyのレンダリング品質はvlibvtermより明らかに上——Emacsでも使えるなら試す価値がある」「libghosttyのAPIがこれほど早くEmacsに来るとは思わなかった。Mitchellのライブラリ設計が良かった証拠」「macOS限定か？LinuxのGTKバックエンドでも動くか気になる」という47コメントが展開しています。
Ghostty / libghosttyとは
Ghostty：Mitchell Hashimoto（Vagrant・HashiCorp創業者）が個人プロジェクトとして開発し2024年12月に公開したターミナルエミュレータ。特徴：macOSネイティブUI・GPU加速レンダリング・完全なVT互換性・Ziglang製で高速。libghostty：Ghosttyのコアロジックをライブラリとして分離したもの。ターミナルエミュレーション・文字レンダリング・エスケープシーケンス処理を提供。目的：Ghosttyの技術をGUI以外のアプリケーション（Emacs等）でも使えるようにする
Emacsターミナルの現状と比較
既存の選択肢：term.el（Emacs付属、古くVT互換性に問題あり）・vterm（libvterm使用、現在の標準的選択肢）・eat（Pure Elispで最近登場）。Ghostel.elの位置づけ：libghosttyのVT100/XTerm互換性はlibvtermより高いとされる——よりモダンなターミナルアプリで使われる高度なエスケープシーケンスが正しく処理される可能性。課題：まだ初期段階——安定性・パフォーマンス・プラットフォームサポートは検証中。vtermユーザーが乗り換えるには実績の積み重ねが必要
Emacsとターミナルの統合という思想
なぜEmacs内にターミナルを持つのか：Emacsをフルの開発環境として使う場合、外部ターミナルに切り替えることなく全ての作業をEmacs内で完結できる。urg（Org-modeでのシェル出力キャプチャ）・コード実行・ファイル操作が一つのバッファ内で統合される。現代的な文脈：VSCodeのIntegrated Terminalと同様の思想——ただしEmacsは40年前からこれを実践してきた。Claude Codeとの統合：Claude Codeをターミナルで使うEmacsユーザーにとって、Emacs内ターミナルとの相性は重要な選択基準になりうる

変わった科学 / 医療 / ワクチン / 認知症 / 予防医療 — 帯状疱疹（シングルス）ワクチンが認知症リスクを大幅に下げる可能性を示す大規模研究。エコノミスト誌が「脳を守る最もシンプルな選択」と評価。183ポイント・162コメント

帯状疱疹
ワクチンが
認知症リスクを
下げる

エコノミスト誌が「A no-brainer for protecting your brain（脳を守るための明快な選択）」を掲載し、183ポイント・162コメントを集めました。記事はウェールズで行われた大規模な自然実験を中心に、帯状疱疹（Herpes Zoster）ワクチンが認知症発症リスクを20〜25%程度低下させる可能性を示す複数の研究を紹介しています。 研究の背景にある仮説はこうです：水痘・帯状疱疹ウイルス（VZV）は子供の頃に感染した後、神経節に潜伏します。加齢とともに免疫力が低下すると再活性化（帯状疱疹として発症）し、一部は脳に炎症を引き起こします。この神経炎症が長期的にアルツハイマー病などの認知症発症に寄与している可能性があるという仮説です。帯状疱疹ワクチン（Shingrix等）がこのリスクを下げることで、副次的に認知症予防効果があると考えられています。 HN上では「これがランダム化比較試験ではなく観察研究であることに注意——ただしウェールズの自然実験（誕生日による接種資格の切断）はかなり信頼性が高い準実験」「Shingrixは高齢者に強く推奨されているが、この研究は接種のインセンティブをさらに強化する」「帯状疱疹ワクチンは保険適用で比較的安価——コストベネフィットを考えると親世代に強く勧める動機になった」という162コメントが展開しています。
研究の根拠と信頼性
ウェールズの自然実験：2013年にウェールズが導入した帯状疱疹ワクチン接種プログラムで、誕生日による資格区切り（70歳直前 vs 直後）が生じた。この「誕生日の偶然」が準ランダム化試験として機能——接種群・非接種群の違いが年齢以外のバイアスを最小化。結果：接種群で7年間の認知症診断が約20%少なかった。他の研究：米国・英国の大規模コホートデータでも同様の傾向。証拠の質：観察研究だが準実験設計で高品質。最終確認にはRCTが望ましいが倫理的に困難
なぜワクチンが認知症を防げるのか（仮説）
VZVと神経炎症：水痘ウイルスは神経節に潜伏し、加齢で再活性化→帯状疱疹→神経炎症が生じる。この慢性的な微小炎症がアルツハイマー病のアミロイドプラーク形成を促進する可能性。支持する証拠：帯状疱疹後神経痛（長期の神経炎症）が認知症リスクを特に高める。感染症と認知症のリンク：単純ヘルペスウイルス（HSV-1）もアルツハイマーとの関連が研究されている——ウイルス性神経炎症仮説全体への関心が高まっている
実際に何をすべきか
対象年齢：帯状疱疹ワクチン（Shingrix）は50歳以上に推奨（米国CDC・日本でも接種可能）。接種スケジュール：2回接種（2〜6ヶ月間隔）。有効率：帯状疱疹発症予防90%以上。副反応：接種部位の痛み・倦怠感は出やすいが数日で解消。日本での状況：定期接種化は未だ限定的——市区町村の補助を確認のこと。親・祖父母世代への勧め：認知症予防の可能性まで加えると、接種を検討する動機がより強くなる。自分が50代以上の場合：今すぐかかりつけ医に相談する価値あり

「絶滅した」
ではなく
「絶版」——
終わり方の哲学

ゲームエンジンのリバースエンジニアリングで知られるFabien Sanglard（ファビアン・サングラード）が「Don't you mean extinct?（絶滅した、ということ？）」を公開し、168ポイント・93コメントを集めました。記事はソフトウェアやテクノロジーが「終わる」ときの2つの異なる在り方——「絶版（discontinued）」と「絶滅（extinct）」——を区別することを提唱する哲学的な考察です。 サングラードの主張は、多くの人が「古いソフト・ハードウェア・ゲームが終わった」と言うとき、実際には2つの全く異なる状態を混同しているというものです。「絶版」は製品が公式サポートを失ったが、まだ動く・使える・コードが存在する状態です。一方「絶滅」は技術的に復元不可能な消滅——ハードウェアが全滅し、ソースコードが失われ、動かすことが不可能になった状態を指します。この区別は単なる言葉遊びではなく、保存活動・エミュレーション・リバースエンジニアリングの意義を正確に定義するために重要だと論じています。 HN上では「Internet Archive・EFFFがこの区別をずっと主張してきた——法的な保存権利の議論においても重要な概念」「コードが『絶滅』しない限り、エミュレーションで復活させる可能性が残る——だからソースコードの保存が重要」「Flashが『絶版』になったとき、Ruffle等のエミュレータでFlashコンテンツを保存できた。真に『絶滅』したFlash作品は今も失われたまま」という93コメントが展開しています。
「絶版」と「絶滅」の違い
絶版（Discontinued）：公式サポート終了・販売終了だが技術的にはまだ動く。例：Windows XP（サポート終了だが仮想マシンで動作可能）・Flash Player（Adobe終了だがRuffleで多くが動く）・PlayStation 2（製造終了だが実機やエミュレータで動作）。絶滅（Extinct）：技術的復元が不可能。例：ハードウェアが全滅し回路図もなく動作実機が存在しない機器・ソースコードが消失しバイナリも残らないソフトウェア・磁気メディアが劣化し読み出せなくなったゲーム。区別の実践的意味：絶版=まだ保存・復元の時間がある。絶滅=手遅れ
デジタル文化の保存問題
規模感：Internet Archiveによると、2000年代初頭のウェブサイトの約40%がすでに「絶滅」状態——キャッシュもアーカイブも存在しない。ゲームの状況：ゲーム保存プロジェクト（Video Game History Foundation等）の推定では、歴史的ゲームの87%が商業的にアクセス不能——ただし「絶版」と「絶滅」の比率は不明。Flashの事例：Adobeの終了発表でInternet Archiveが大規模なFlash保存プロジェクトを実施→Ruffle等のエミュレータ開発につながった。教訓：「絶版」の段階で動くなら、今すぐ保存できる
ファビアン・サングラードの視点
著者の背景：Doom・Quakeなどのゲームエンジンをリバースエンジニアリングして解説することで有名。「絶版」ゲームのコードを読み解くことで技術史を書いてきた研究者的視点を持つ。主張の核心：リバースエンジニアリングや保存活動の意義は「絶版」の段階で行動することにある。一度「絶滅」したものは取り戻せない。個人ができること：大切なソフト・ゲーム・デジタルコンテンツは「絶版」の段階でバックアップ・アーカイブを取る。GOG.com・Internet Archive・emulation projectsへの支持が「絶滅」を防ぐ

技術的詳細：Math.tanh(x)はIEEE 754準拠だが内部アルゴリズムはOS依存。macOS（libm）・Linux（glibc）・Windows（msvcrt）で計算経路が異なり、最下位の数ビットが異なる結果になる。Chromium 148の変更：この差異がより顕著になる計算パスに移行。具体例：Math.tanh(1) → 全OS共通だが、Math.tanh(0.000001) → 最下位2〜3ビットがOS間で相違。識別精度：特定の入力値を複数試すことで、macOS/Linux/Windowsの3択を95%以上の精度で識別可能とのこと

主なフィンガープリント手法（Math.tanh以外）：①Canvasフィンガープリント（GPU・フォントレンダリングの差異）②WebGLフィンガープリント（GPUモデルの識別）③AudioContext（音声処理の差異）④フォントリスト⑤画面解像度・タイムゾーン⑥バッテリー情報（廃止済みだが過去は使われた）。組み合わせの脅威：個々のシグナルは数ビット程度のエントロピーだが、10〜20個組み合わせると実質的なユニーク識別が可能。Math.tanhは「OS種別」を数ビット追加するもの

ブラウザ側の対策：Firefoxの「fingerprinting resistance」モードで浮動小数点結果にノイズを加算。ただしこれ自体がFirefoxシグナルになる。Tor Browser：最も強力な対策だが使いやすさとのトレードオフ。実用的なアドバイス：フィンガープリント対策の完全な回避は現実的でない。代わりに①同一ブラウザを複数サービスに使わない②Brave Browser（フィンガープリント対策内蔵）を検討③追跡が問題になる場合はTorを使う。重要な認識：ブラウザの「プライベートモード」はフィンガープリントを防がない——IPアドレスとCookieを隠すだけ

論文の定義：局所的な有能さ（Local Competence）＝特定の状況・パターンで正しい行動を取れること。大域的な理解（Global Understanding）＝なぜその行動が正しいかを知り、新しい状況に応用できること。LLMの現状：局所的有能さは高い（コードのデバッグ・既知パターンの適用）。大域的理解は不安定——訓練分布外の問題で急激に能力が落ちる。具体例：コーディングエージェントがよく知ったライブラリのバグは直せるが、そのライブラリを使わない設計判断の是非は判断できない
