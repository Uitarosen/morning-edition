BunのRustリライト——
7ヶ月後の
正直
レポート

JavaScriptランタイム「Bun」のチームが、ZigからRustへのリライト作業の進捗を詳細な記事として公開し、428ポイント・323コメントを集めました。Bunはjarred Sumner氏が主導し、Node.jsよりも高速なJS/TSランタイムを目指してZigで書かれてきましたが、特定のコンポーネントをRustに移行している経緯とその結果を報告したものです。 記事ではRustへ移行した理由として「Zigのエコシステムが未成熟でコントリビューターが集まりにくい」「Cratesに良質なライブラリが多く、特に非同期I/O（Tokio）周りで再利用できる資産が豊富」という点を挙げています。一方でZigが良かった点として「MIMEパーサーやHTTPコアなどパフォーマンスクリティカルな部分はZigの方が柔軟なメモリ制御ができる」という評価も率直に述べており、現実的には「Zig + Rust のハイブリッド」構成が続く見通しです。 HN上では「Zig→Rust という方向は先週話題になったRust→Zig（Rocコンパイラ）と逆方向——どちらも一長一短がある」「BunのZig部分は本当に速い、パフォーマンスを犠牲にせずRustに移行できるかが課題」「Rustのコントリビューターを集めやすいのは現実的な理由——OSSプロジェクトの持続可能性に関わる」という323コメントの議論が展開されました。
なぜRustへ移行するのか
Zigのエコシステムの未成熟さ：ZLS（Language Server）が不安定、ライブラリが少ない。Rustのコントリビューターを集めやすい：crates.io + GitHub上のRust開発者人口が圧倒的に多い。Tokio（非同期I/O）：成熟した非同期ランタイムを再利用できる。パフォーマンス：RustもZigと同様にゼロコストアブストラクションが可能（バウンダリ次第）
ZigをRustより優れると判断した部分
MIMEパーサー・HTTPヘッダー処理：非常に細かいメモリレイアウト制御が必要な部分はZigが有利。コンパイル時計算（comptime）：型レベルのメタプログラミングがRustマクロより直感的。C FFI：FFI境界がRustより薄く、外部ライブラリ統合がシンプル。「パフォーマンスが最優先の100行未満の関数」はZigのままにする設計方針
Bunユーザーへの影響
API・CLIインターフェースに変化なし。パフォーマンスは段階的に維持・改善される見込み。Rustリライトにより安定性（クラッシュバグ減少）と機能追加速度が向上することを期待。短期的には一部モジュールでリグレッションリスクがあり、v1.2.x系でのリリースに注意。npm互換性の強化がRust移行の優先課題の一つ

ReactをHTMXで
置き換えた——
コードベース
刷新の実録

DjangoベースのフォーラムソフトウェアMisagoの開発者Rafał Pitoń氏が、フロントエンドのReact.jsを全廃してHTMXに移行したプロセスを詳細に記述した記事が199ポイント・147コメントを集めました。2023年の記事が今も読まれ続ける理由は、「React vs. HTMXのどちらを選ぶか」という議論がいまだに現役であることを示しています。 移行の動機として「React SPAはSSR/SEOとの相性が悪く、Djangoのテンプレートエンジンと2重管理になっていた」「フロントエンドのビルドパイプライン（webpack・babel・npm）の管理コストが小規模チームに重かった」「Reactの状態管理の複雑さが新機能追加のスピードを落としていた」という3点が挙げられています。HTMXへの移行後は「Django側でHTMLを生成してHTMXでDOMを差し替えるだけ」というシンプルな構造になり、コードベースの行数が大幅に削減されたと報告しています。 HN上では「HTMXはReactの全てのユースケースをカバーはしない——リアルタイム・複雑な状態管理が必要なアプリは別話」「小〜中規模のサーバーサイドアプリにはHTMXは本当に良い選択」「Django + HTMXはRailsとHotwireの関係に似ている——どちらもフルスタックの本来のシンプルさを取り戻す試み」という147コメントが展開されました。
ReactをやめてHTMXを選んだ理由
Django + React は「テンプレート2重管理」問題：バックエンドとフロントエンドで同じUIロジックを2回書く。ビルドパイプラインのコスト：webpack・babel・package.json管理が小チームに重い。SEO・SSR との相性：ReactのSPAはDjangoのURLルーティング・SEOと衝突しやすい。HTMX：HTMLにhx-get/hx-postなどの属性を追加するだけでDOMを更新——Djangoのビューが主役に戻る
移行後の変化
JS ファイル数の激減：React のコンポーネント群が消え、HTMXのCDN 1行に置き換わった。ビルドステップが不要に：npm run build が消えた。Django View が「真実の源」に：UIとデータ処理が一か所に集まった。デバッグのシンプル化：ネットワークタブを見れば全てわかる構造に。新機能追加が速くなった：バックエンドエンジニアが直接フロントを触れるようになった
HTMXが向かないケース
リアルタイム同期が必要な複雑UI（共同編集・ゲーム・株価チャート等）。クライアントサイドの複雑な状態管理（多段フォーム・ドラッグ&ドロップ・リッチエディタ）。APIファーストでモバイルアプリもバックエンドを共用するケース。これらは素直にReact/Vue/Svelteを選ぶべき。「フォーラム・CMS・管理画面・SaaS基盤」などはHTMXが輝くカテゴリ

プライバシー / 法律 / Google / DMCA / スクレイピング / 著作権 / TechDirt — GoogleがDMCA（デジタルミレニアム著作権法）を盾に自社サービスへのスクレイピングを阻止しようとした訴訟で、判事がその試みを却下。スクレイピングの合法性をめぐる重要判決。193ポイント・73コメント。2026-07-27

判事がGoogle
のDMCAによる
スクレイピング
排除を却下

TechDirtが報じたところによると、GoogleがDMCA（デジタルミレニアム著作権法）を利用して自社サービスへのスクレイピングを阻止しようとした法的な試みを、判事が却下したことが明らかになりました。193ポイント・73コメントを集め、ウェブスクレイピングの合法性とプラットフォームの利用規約の力関係をめぐる重要な判決として注目されています。 Googleはある事業者による自社検索結果・マップデータ等へのスクレイピングをDMCAに基づく著作権侵害として訴えようとしました。しかし判事は「ウェブスクレイピング自体はDMCAが対象とする技術的保護手段の回避には当たらない」「robots.txtやToSへの違反は別の法的枠組みで扱う問題であり、DMCAの著作権侵害とは別」として、GoogleのDMCAによるアプローチを退けました。これはhiQ v. LinkedInなどの先行判決の流れと一致する方向性です。 HN上では「GoogleはDMCAをスクレイピング排除の武器として使いたかった——却下されたことは公共のウェブへのアクセスにとって重要な勝利」「hiQ v. LinkedIn（最高裁相当）に続く判例の積み重ね——スクレイピングはComputer Fraud and Abuse Actでも訴えられにくくなっている」「皮肉なのは、Googleが最もウェブをクロール・スクレイピングした企業だという事実」という73コメントが展開されました。
判決の要点
DMCAはスクレイピングに適用されない：「技術的保護手段（DRM等）の回避」をカバーするDMCAは、単なるHTTPアクセスによるスクレイピングには適用できないと判示。ToS違反は別問題：利用規約（Terms of Service）へのスクレイピング禁止条項違反は、契約違反（民法的）の問題であり、DMCAの著作権侵害とは別の枠組みで争うべき。パブリックウェブへのアクセスを著作権法で制限することへの司法の否定的スタンスが明確化された
先行判例との関係
hiQ v. LinkedIn（2022年最高裁）：LinkedInが公開プロフィールのスクレイピングをComputer Fraud and Abuse Act（CFAA）で訴えた件で、最高裁はhiQ側に有利な判断を下した。今回はDMCAを使ったGoogleの試みを退けた追加事例。「CFAAもDMCAも使えない」という方向で先例が積み重なりつつある。スクレイピングを法的に防ぐ手段としてToS+契約法・robots.txt+技術的制限が残る構図
AI企業・開発者への影響
LLM学習データ収集：この判例はスクレイピングによる学習データ収集の合法性に有利な方向。プロキシ・API開発者：公開データへのアクセスツールを作る開発者に安心材料。一方でToS（利用規約）：DMCAが使えないだけで、ToS違反による契約訴訟は依然として有効な法的手段。Googleが次に試みる法的戦術（ToS基盤の差止請求等）に注目が集まる

Andros氏のブログ記事「Modern email can be built from borrowed parts」が163ポイント・91コメントを集めました。「独自のメールサービスを作るのは難しい」という一般的な認識に対して、既存のオープンプロトコル（SMTP・IMAP・DKIM・SPF・DMARC等）を組み合わせることで、意外にシンプルにモダンなメールインフラを構築できるという論考です。 記事ではメールシステムを「MTA（Mail Transfer Agent）、MSA（Mail Submission Agent）、MDA（Mail Delivery Agent）」の3つのコンポーネントに分解し、それぞれにPostfix・Dovecot・Haraka等の実績あるOSSを当てはめるアーキテクチャを解説しています。著者は「メールの難しさの多くは技術的な難しさではなく、スパムフィルタリング・IPレピュテーション・大手プロバイダとの相互運用性というエコシステムの問題だ」と指摘しており、技術的な実装自体は既存ライブラリで再現可能だという主張です。 HN上では「メールは『作るのが難しい』のではなく『届けるのが難しい』——Gmailに届かないメールを送らないようにするのが最大の課題」「Postalやmailinaboxみたいな既成ソリューションが既にあるが、自前でやるコントロール感は確かにある」「SPF・DKIM・DMARC・ARC・BIMIを全部正しく設定するのは思ったより複雑——それでもこの記事の主張は正しい」という91コメントが展開されました。
メールシステムの3コンポーネント
MTA（Mail Transfer Agent）：メールを他のサーバーと送受信する。Postfix・Exim・Harakaが代表例。SMTPで通信。MSA（Mail Submission Agent）：クライアントからメールを受け取ってMTAに渡す。認証・レート制限を担当。MDA（Mail Delivery Agent）：受信したメールをユーザーのメールボックスに格納する。Dovecot・Procmailが代表例。IMAP/POP3でクライアントに配信。「借り物パーツ」= これらを組み合わせるだけ
技術的ではなくエコシステムの問題
IPレピュテーション：新しいIPはスパマー扱いされやすく、Gmailなどに届くまで「warming up」期間が必要。SPF・DKIM・DMARC：認証レコードの設定ミスで迷惑メール判定される。フィードバックループ：大手プロバイダへの苦情（FBL）管理が必要。バウンス管理：ハードバウンスを放置するとIPスコアが下がる。「これらを理解した上なら、技術的な実装自体は難しくない」が著者の主張
自前構築 vs. SendGrid/SES
自前のメリット：コスト（大量送信では大幅に安い）、データコントロール（メール内容を外部に渡さない）、カスタマイズ性。SendGrid/SES のメリット：IPレピュテーション管理不要、設定が最小限、サポートあり。中間の選択肢：VPS上にMailcow・Mailu・mailinaboxをDockerで立ち上げる（半自前）。「送信量1万通/月以下ならSES/SendGridが圧倒的にコスパ良い」という結論をコメント欄では共有

三色マーク＆スウィープとは
白（未処理）・グレー（処理中）・黒（処理済み）の3状態でオブジェクトを管理。GC開始時：全オブジェクトが白。到達可能なルート（スタック変数・グローバル変数）からグレーに変換。グレーオブジェクトの参照先をグレーに変換し、自分は黒に変換。最終的に白のまま残ったオブジェクトが「到達不可能 = 回収対象」。並行実行：アプリケーションの実行と並行してGCが動くためSTWが最小限になる

Write Barrierの最適化：アプリケーションがポインタを書き換えるたびにGCに通知するオーバーヘッドを削減。STW短縮：「Final Sweep」フェーズのSTWを最小化し、p99レイテンシを削減。ヒープのセグメント化：連続するメモリブロックの管理を改善しフラグメンテーション低減。メモリ割り当て速度向上：スレッドローカルキャッシュ（mcache）の効率化。GC pacing：GCサイクルのタイミングをワークロードに合わせて自動調整

Uncle Bobが言いたいこと
AIエージェントのコードは「人間が書くコードの代わり」ではなく「別種の成果物」として扱うべき。評価基準の転換：可読性・命名規則（人間向けの指標）ではなく、テストカバレッジ・型安全性・実行結果（機械で検証可能な指標）で品質を担保。「コードの理解」から「コードの動作の理解」へ。これは極端だが、AI生成コードへの付き合い方を問い直す挑発的な提言として読める
賛成側の論拠
AIコードは読む価値が低い：AIが最適化したコードは人間の読みやすさを考慮していない場合が多い。テスト・型・Lint が「正しさ」の証明になる：動くことを証明できれば実装詳細は問わない。スケールの問題：AIが1000行/分生成するコードを人間がレビューするのは非現実的。将来的に：コードは機械が読み、人間は仕様・テスト・インターフェースだけを管理する世界になる可能性がある
反対側の懸念
セキュリティ：AIが生成したコードはハルシネーションや脆弱なパターンを含む可能性がある——テストで全てを検出できるとは限らない。保守性：誰もコードを理解していない状態は、バグ修正・機能追加を困難にする（知識の消失）。法的リスク：著作権・コンプライアンス・機密保持の問題がコードに潜む可能性がある。テストの網羅性：テストが通れば安全というのは「テストされていないバグはない」という誤謬に近い
