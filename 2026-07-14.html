TechCrunchが報じた通り、ロサンゼルス市警察（LAPD）が自動車ナンバープレート認識（ALPR）サービス大手のFlock Safetyとの契約を更新せず失効させました。LAPDが公式に認めた理由は「市民の自由とプライバシーに関する深刻な懸念（serious concerns over civil liberties and privacy）」で、405ポイント・321コメントという活発な議論を呼んでいます。 Flock Safetyはアメリカ中に広がるカメラネットワークを通じて、車のナンバープレートと移動パターンを大規模に記録するシステムです。警察との契約により、リアルタイムで住民の移動を追跡できます。LAPDは2020年代に複数の自治体がFlock導入を進める中で契約していましたが、プライバシー擁護団体からは一貫して「令状なしの大量監視を可能にする」と批判されていました。 HN上では「一つの警察署が良心的な決断をしたことは良いが、Flockの契約数は増え続けている——LAPDはニュースになるだけで例外」「ALPRデータは一定期間保存される——誰がそのデータにアクセスできるか、どのくらい保存されるかが問題の核心」「Flockが使うのはカメラだけでなく既存の民間監視インフラも活用している——問題はFlock固有ではなくエコシステム全体」という321コメントが展開しています。
Flock Safetyの規模
4,000以上の自治体
全米で契約中。ALPRカメラネットワークが車のナンバーと移動パターンを24時間記録。データは警察がリアルタイムで参照可能
LAPDの決断
契約を失効（更新せず）
「市民の自由とプライバシーへの深刻な懸念」を明示。大規模警察署がFlock契約を打ち切る珍しい事例。他自治体への波及効果に注目が集まる
何が問題か
令状なし大量追跡
EFFが長年批判。個人の通常の移動が記録・蓄積される「大量監視」。特定の人物のみ追跡する従来の手法と根本的に異なる

セキュリティ / Linux / 脆弱性 / UAF / カーネル — Nebusec AIのリサーチがLinuxカーネルに15年以上潜んでいたstack-UAF（Use After Free）脆弱性「GhostLock」を詳細に解説。全ディストリビューションが影響を受ける。386ポイント・186コメント

GhostLock——
15年間全Linuxに
潜んでいた
stack-UAF

Nebusec AIのセキュリティ研究者が公開した「GhostLock」のION stackに関する第2弾レポートが386ポイント・186コメントを集めました。この脆弱性はLinuxカーネルのIONスタック実装に存在するstack-UAF（Use After Free）であり、実質的に全てのLinuxディストリビューションが約15年以上にわたり影響を受けていたことが示されています。 UAF（Use After Free）はメモリ安全性の脆弱性で、解放済みのメモリ領域を引き続き参照・使用することで発生します。stack-UAFはその亜種で、スタック上のローカル変数が関数終了後も参照される状況です。GhostLockの場合、Linuxのロック機構がコンテキストスイッチのタイミングで解放済みスタックフレームへの参照を残すことが問題の核心です。研究者はPoCエクスプロイトを開発しており、適切な条件下でのローカル権限昇格が可能とされています。 HN上では「15年間気づかれなかったのは、実際の悪用が難しいから——タイミング依存でレースコンディションを要求するため」「IONはAndroidでも多用されているが、Androidのサンドボックスが追加の緩和層を提供している」「Rustで書き直されていれば……というのは置いておいて、この種のバグをコードレビューで発見するには静的解析ツールの組み合わせが必要」という186コメントが展開しています。
脆弱性の性質
stack-UAF（Use After Free）：関数スコープ外のスタック変数をLock機構が参照し続ける。Linux IONスタック（メモリ管理サブシステム）に存在。マルチスレッド・コンテキストスイッチのタイミングで再現可能なレースコンディション
影響範囲
全Linuxディストリビューション（Ubuntu, Debian, Fedora, Arch等）。Linuxカーネル搭載Androidデバイスも影響下。約15年以上にわたり修正されないまま存在していた。ローカル権限昇格（LPE）のベクタになりうる
なぜ15年間気づかれなかったか
悪用に必要な条件が複雑：特定タイミングのレースコンディション + 特定カーネル設定 + ローカルアクセス。リモートエクスプロイトではなくローカルのみ。ファジングが見逃しやすい「静的に安全に見えるが動的に危険」なパターン

Apple

精度（英語WER）
SpeechAnalyzer API：Whisper large-v3に匹敵またはわずかに上回る。前世代Speech Framework比で大幅改善。ただしベンチマークデータセット依存——一般的な話し言葉での比較が必要

制限・注意点
多言語サポートはWhisperが優位。iOS 26 / macOS 16以降限定——古いOS非対応。APIはAppleのサンドボックス内——モデルの詳細は非公開。非英語での精度データがまだ不足

Climate.govは
破壊された。

救った

werd.ioに掲載されたエッセイ「Climate.gov was destroyed. 何が失われたか
Climate.gov：海面上昇データ、海水温記録、気象イベント統計、気候変動指標などの科学的データセット。一般市民・研究者・ジャーナリストが使う公共情報。NOAA予算削減と政治的判断による縮小・廃止
どう救われたか
Internet Archive（Wayback Machine）が削除前にページをクロール。研究機関・大学が独自にデータをミラーリング。GitHubのオープンデータプロジェクトが再構築・再配布。「End of Term」ウェブアーカイブプロジェクトが政権交代前に大規模クロールを実施
教訓
公共データは「存在する」と「アクセスできる」は別物。オープンライセンスでも配布インフラが消えれば実質的に失われる。民間ボランティアの先制的なアーカイビングが公共財の最後の防衛線になっている現実

Xcodeを一度も

Scott Willseyが自身のブログで公開した「Building and Shipping Mac and iOS Apps Without Ever Opening Xcode」が185ポイント・80コメントを集めました。Xcodeは巨大なIDEで多くのMac開発者にとって「必要だが重い」存在です。この記事ではXcodeをインストールするがGUIを一切使わず、CLI・SwiftPM・xcodebuild・fastlaneなどを組み合わせることで完全なビルド・テスト・署名・リリースパイプラインを構築する方法を詳細に解説しています。 著者のアプローチはエディタとしてNeovimまたはVS Codeを使用し、Swift Package Manager（SPM）でプロジェクト管理、xcodebuildでビルド、fastlane Matchで証明書・プロビジョニングプロファイル管理、fastlane Deliverでストア提出という構成です。デバッグにはlldbをCLIで直接使用します。CIでの自動化との相性が非常に良く、Xcodeのプロジェクトファイル（.xcodeproj）の競合問題からも解放されます。 HN上では「Xcodeのプロジェクトファイルのgit conflictはチームで最も嫌われるものの一つ——SPM + CLIに移行するとそれが消える」「xcode-selectとxcodebuildの組み合わせはCI（GitHub Actions, Bitrise等）での標準的なアプローチ——今さらというコメントも多いが丁寧なまとめ」「Apple Siliconになってからビルドが速くなったのでCLIオンリーの快適さが増した」という80コメントが展開しています。
必要なツールチェーン
Xcode（インストールのみ、GUIは使わない）+ Command Line Tools。エディタ：Neovim / VS Code / Emacs / お好みのもの。ビルド：xcodebuild + Swift Package Manager。証明書管理：fastlane Match。ストア提出：fastlane Deliver または altool
なぜXcodeを避けたいのか

実用上の注意点
InstrumentsなどプロファイリングツールはXcodeに依存。Interface Builder / SwiftUI Previewのリアルタイムプレビューはできない。新しいApple APIの実験・プレビュー機能はXcode GUIが便利。完全移行より「普段はCLI、必要時だけGUI」のハイブリッドが現実的

Sega CD

Telegramの
t.meドメインが
停止——
何が起きているのか

HNユーザーがTelegramのグループ・チャンネル共有に使われるショートリンクドメイン「t.me」が停止状態（suspended）になっているとwhoisから確認されたと投稿し、181ポイント・95コメントを集めました。t.meはTelegramのパブリックリンクに不可欠なドメインで、これが停止すると「@username」形式の全てのショートリンクが機能しなくなります。 投稿時点ではドメインのwhoisで「clientHold」ステータスが報告されており、これはレジストラまたはレジストリによる強制的な停止を意味します。Telegramはセキュリティ機能・プライバシー機能を理由に各国の規制当局から度々圧力を受けており（フランス・EU・ブラジル等）、ドメイン停止が規制執行の一形態として使われた可能性が議論されています。ただし技術的な一時障害の可能性も排除できず、コメントが投稿された後に復旧したという報告もあります。 HN上では「ドメインのclientHoldは規制当局からの要請でレジストラが処理する標準的な手順——しかしt.meはMonaco（.me）ドメインでモンテネグロのレジストリ管轄、どの政府が介入できるか複雑」「Telegramはこのリスクに備えてIP直接接続や分散型フォールバックを持っているはず」「プラットフォームの通信インフラをDNSに依存させることの脆弱性——Signal、Mastodon等も他人事ではない」という95コメントが展開しています。
clientHoldとは何か
ドメインのEPPステータスコードの一つ。レジストラ（ドメイン販売業者）がドメインを一時停止する状態。DNS解決が機能しなくなり、そのドメインへのアクセスが全て失敗する。原因：法的命令、規制当局の要請、支払い問題、不正使用報告など
t.meが停止するとどうなるか
t.me/username 形式の全パブリックリンクが機能しない。グループ招待リンク・チャンネルリンクが使えなくなる。Telegram Webアプリ（web.telegram.org）は別ドメインのため影響は別。モバイルアプリは直接接続を試みるため部分的に機能する可能性

DOM-docx——
HTMLから
ネイティブな
Wordドキュメント

MITライセンスのOSSライブラリ「DOM-docx」がShow HNで128ポイント・30コメントを集めました。このライブラリはHTMLをパースして、編集可能なネイティブの.docxファイルとして出力します。PDF変換ではなく、Wordで開いて実際に編集・書式変更できるdocxが生成されます。ブラウザとNode.jsの両環境で動作するため、フロントエンドでもバックエンドでもドキュメント生成に使えます。 既存のHTML→Wordソリューション（html-docx-js等）はHTMLをWordのリッチテキスト互換フォーマットに変換するため、実際に開いたときに書式が崩れたり、Wordの編集機能が制限されるケースがありました。DOM-docxはDocx Open XML仕様を直接生成するアプローチを取っており、段落・見出し・テーブル・インライン画像などがWordのネイティブ要素として出力されます。スタイルのマッピングもカスタマイズ可能で、既存のWordテンプレートに流し込む用途にも対応しています。 HN上では「自動生成レポートをWord形式で出力するニーズは非常に多い——PDFは編集できないが顧客がWordで欲しいというケースがほとんど」「docxのOpen XML仕様は複雑すぎて手書きは辛い——こういうアブストラクション層が必要」「MITライセンスかつブラウザ対応は貴重——既存のドキュメント生成ライブラリは商用ライセンスが多い」という30コメントが展開しています。
従来のHTML→Word変換との違い
従来（html-docx-js等）：WordのリッチテキストフォーマットにHTML相当のマークアップを埋め込む。結果：書式崩れ、編集制限、古いWordとの互換性問題。DOM-docx：Open XML仕様でネイティブdocx要素を直接生成。結果：Wordの全機能が使える、スタイル継承が機能する、テンプレートへの流し込みが可能
実用ユースケース
Webアプリからのレポート・請求書・契約書のWord出力。CMSのコンテンツをWord形式でダウンロード。Eメールのテンプレートを編集可能なWordドキュメントに変換。既存のWordテンプレートに動的データを流し込み。バックエンドでのバッチドキュメント生成（Node.js）
技術仕様
ライセンス：MIT（商用利用可、無料）。動作環境：ブラウザ（モダンブラウザ全般）+ Node.js。出力：OOXML準拠の.docxファイル。対応要素：段落、見出し（H1-H6）、テーブル、インライン画像、リスト、インラインスタイル（太字・斜体・色）
