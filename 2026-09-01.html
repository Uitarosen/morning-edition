Claude Code
Opus 5の
Auto Modeを破る——
セキュリティ研究

セキュリティ研究者のembracethered.comが「Breaking Claude Code Opus 5 Auto Mode」を公開し、327ポイント・110コメントを集めました。Claude CodeのAuto Mode（自動承認モード）において、悪意のあるプロンプトインジェクションやコードリポジトリ内の仕掛けを通じて、本来ユーザーの確認が必要な操作（ファイル削除・外部コマンド実行・機密情報の送信）を無断で実行させることができるという研究です。 Auto Modeの強力さと自律性が生み出す新しい攻撃面——「AIエージェントを操ってそのコンテキスト内で悪意ある操作を実行させる」という脅威モデルは、Claude Codeを業務で使用している開発者にとって直接関係する内容です。研究者はAnthropicに事前通知した上で責任ある開示を行っています。
攻撃の仕組み
リポジトリ内の隠された指示でAIを操作
研究者が実証した手法：①コードコメント・READMEファイル・設定ファイル内に「Claude Codeへの指示」を埋め込む。②Auto Modeで実行中のClaudeがそのファイルを読むと、埋め込まれた指示に従って意図しない動作（curl送信・環境変数の外部転送・ファイル削除）を実行する。③ユーザーはAuto Modeのため確認ダイアログが表示されず、操作に気づかない。
Anthropicの対応
研究を受けてAuto Modeの制限を強化
Anthropicは本研究を「責任ある開示」として受け取り、いくつかの緩和策を実施済みとのこと。具体的には：①破壊的操作（rm・curl等）はAuto Modeでも再確認を要求するよう変更。②システムプロンプトレベルでの「Auto Mode有効フラグ」をコンテキストから読み取れる形で提供し、モデルが自身の実行環境を認識できるようにする対策を検討中。
今すぐできる対策
信頼できないリポジトリでAuto Modeを使わない
HNコミュニティと研究者が推奨する実践的対策：①クローンしたばかりの外部リポジトリでAuto Modeを起動しない。②`CLAUDE.md`や`.claude/`ディレクトリの内容を必ず事前確認する。③重要な操作は`--dangerously-skip-permissions`フラグなしで実行し、確認プロンプトを有効に保つ。④AIエージェントがアクセスするファイルを「コード」として扱い、サプライチェーンセキュリティと同様の意識を持つ。

軍の売店の
冷凍庫がハッキング
されたかも
しれない

signalandsilence.substackのライターが「I think the military commissary's freezers were hacked」という体験レポートを公開し、197ポイント・116コメントを集めました。米軍の売店（commissary）で、冷凍食品を保管するすべての冷凍庫が同時に温度設定を失い、一晩で大量の食品が解凍・廃棄されるという事態が発生。筆者がOT（Operational Technology）セキュリティの観点からその原因を推測・分析した内容です。 工場・施設インフラのスマート化が進む中、ネットワーク接続された産業制御システム（ICS/SCADA）のセキュリティが脆弱なケースは珍しくなく、「冷凍庫のIoT化」というありふれた現代の設備が重要インフラへの攻撃面になり得るという事実を具体的な事例で示しています。
何が起きたのか
事件の概要：米軍売店の全冷凍庫が同夜に正常温度から逸脱し、翌朝には大量の冷凍食品が廃棄不可避の状態に。特徴的な点：①全ての冷凍庫が「同時に」異常を起こした——個別の機械故障ではなく、一括管理システムへの干渉を示唆。②温度ログには異常なコマンドの痕跡があったと筆者は主張。③施設のITセキュリティ担当は「調査中」としてそれ以上の情報を開示しなかった。筆者の分析：施設の温度管理はBACnet・Modbus等の産業プロトコルで接続された統合管理システムに依存しており、そこへの不正アクセスが疑われる。
OTセキュリティの現実
HNの議論が掘り下げたOT（Operational Technology）セキュリティの問題：①多くの施設制御システムはインターネット時代より前に設計されており、認証・暗号化が皆無か著しく弱い。②メーカーがリモート管理のためにデフォルトでポートを開放するケースが後を絶たない。③「エアギャップ」（物理的分離）が信じられているが、メンテナンス用のセルラー接続・ベンダーのリモートアクセスなどで実際には繋がっているケースが多い。実例：Shodan.ioで「BACnet」「Modbus」を検索すると、認証なしで到達できる産業制御機器が世界中で数万台見つかる。
HNの反応と教訓
コメントで多く指摘された点：「軍施設でこのレベルのOTセキュリティなら、民間の食料品チェーン・病院・電力施設はさらに脆弱なはず」。懐疑的な声：「単純な機器故障や設定ミスの可能性があり、ハッキングと断定するには証拠が足りない」——著者も可能性として論じていることを注記。重要な教訓：①コネクテッドIoT機器の導入前にネットワーク分離ポリシーを定める②産業制御システムのデフォルト認証情報を必ず変更する③ログは改ざん不可能な形式で外部に保存する④ベンダーのリモートアクセスは最小権限・時限付きで管理する。

GoogleがMV2
拡張機能を
ウェブストアから削除——
uBlock Originも含む

GoogleがManifest V2（MV2）ベースのChrome拡張機能をChromeウェブストアから正式に削除し始め、最も人気の広告ブロッカー「uBlock Origin」も対象になっていると報告されました。161ポイント・117コメントを集め、プライバシーとウェブの自由を重視するHNユーザーから強い反応を引き起こしています。 Manifest V3（MV3）への移行はGoogleが長年推進してきた変更で、「セキュリティの向上」を名目としつつも広告ブロック機能を実質的に制限するものとして批判を受け続けてきました。MV2に依存するuBlock Originは完全なMV3版（uBlock Origin Lite）への移行を進めてきましたが、フル機能からは劣ると評価されており、ユーザーへの影響は避けられない状況です。
MV2からMV3への変更で何が変わるのか
技術的な変更点：MV2では拡張機能がリクエストを動的にインターセプト・変更できる（webRequest API）。MV3ではルールベースのdeclarativeNetRequest APIに置き換えられ、①同時に適用できるルール数に上限が設けられた（30,000件、MV2は事実上無制限）②動的なリクエスト分析ができなくなった③コスメティックフィルタリングの一部機能が制限された。広告ブロッカーへの影響：uBlock Originはフィルタリストを動的に適用する高度な機能に依存しており、MV3のルール上限ではfanboy-social・uAssets等の大規模リストを完全に適用できない。
ユーザーの選択肢
現時点での代替手段：①Firefox＋uBlock Origin（MV2継続サポート）——最も確実な選択肢。FirefoxはMV2を今後も維持すると表明。②Brave Browser——組み込みの広告ブロッカーがエンジンレベルで動作するためMV2/V3の制限を受けない。③Arc Browser（MV3対応）——独自のコンテンツブロック機能を持つ。④uBlock Origin Lite（MV3版）——機能は限定されるがChromeで継続利用可能。⑤Pi-hole等のDNSレベルブロッキング——ネットワーク全体に適用、ブラウザに依存しない。HNで最多upvoteのアドバイス：「これを機にFirefoxに乗り換えることを真剣に検討すべき」。
HNの反応と今後の展開
強い反発：「Googleは検索・ブラウザ・広告の三位一体で広告エコシステムを支配しており、広告ブロックの制限はそのビジネスモデルへの直接的な利益誘導」という批判が多数。Googleの主張：「MV3はセキュリティを向上させる——拡張機能がリクエストを動的に変更できることはプライバシーリスク」。反論：「その論理なら広告ネットワーク自身がトラッカーで動いている矛盾をどう説明するのか」。長期的な影響：Chromeのシェアが依然80%近くある中でのこの変更は、ウェブ広告エコシステム全体に影響する——既にFirefoxのダウンロード数が増加しているとの報告あり。

NATの技術的影響：IPv4アドレス枯渇への応急処置として普及したNATは、全てのデバイスがユニークなIPアドレスを持つという「インターネットの本来の設計」を壊した。結果として生じた問題：①任意の2台のPCがNAT越しに直接通信するには「ホールパンチング」等のハックが必要。②自宅サーバーへの外部からの接続が事実上不可能になり、「サーバーを自分で立てる」文化が廃れた。③WebRTC・Torrent・BitcoinなどP2P技術がNATを回避するために複雑な中継（STUN/TURNサーバー）に依存することになった。④中継を提供できる大規模インフラを持つ企業が不可欠な存在となり、中央集権化が進んだ。

IPv6によるNAT問題の解消：IPv6では全デバイスがグローバルにユニークなアドレスを持てる——理論的にNATは不要で、P2P・自己ホストが復権できる。現実：2026年時点でIPv6の普及率はグローバルで50〜60%程度。日本では主要ISPの対応が進んでいるが、家庭用ルーターのIPv6デフォルト設定が適切でないケースが多い。HNコメント：「ISPがIPv6のデプロイを急がなかったのはNATが事実上のファイアウォールになっていてセキュリティコストを削減できたから——IPv6化すると各デバイスが露出するため正式なファイアウォール管理が必要になる」。
