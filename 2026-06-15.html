Kageとは
ウェブサイトを丸ごとクロールしてシングルバイナリに変換するCLIツール。バイナリを実行するとローカルサーバーが起動してブラウザでオフライン閲覧が可能。HTML・CSS・JS・画像・フォントなど全アセットをバイナリに内包。github.com/tamnd/kage で公開中

リオの「自作LLM」は
モデルのマージだった
——GitHub Issueが
全てを暴露

リオデジャネイロ市が「自社開発」と発表したLLM「Nex-N2」が、実際には既存のオープンソースモデルのマージ（合体）に過ぎないことが、GitHub Issueへの投稿によって暴露され、234ポイント・128コメントを集めています。Nex-N2はブラジル政府系の「nex-agi」というOrganizationが公開したモデルで、リオデジャネイロ市が「ブラジル独自のAI」として発表したものでした。しかし調査した研究者がモデルの重みを分析したところ、実際には既存のオープンソースモデル（MetaのLlamaベースと推測）を複数組み合わせたマージモデルであることが判明。オリジナルのトレーニングはほぼ行われていないというのが結論です。これはAIの「自社開発」という主張が実態と乖離している例として注目を集めています——政府や企業がオープンソースモデルをマージ・微調整して「自社AI」と主張するケースは世界中で増えており、透明性の問題が改めて浮き彫りになりました。HNでは「モデルマージ自体は悪くない——問題はそれを『独自開発』として発表した誠実さの欠如」「オープンソースモデルのマージを許可ライセンスの範囲で使うのは合法——しかし政府プロジェクトとしての説明責任は別の話」「モデルのフィンガープリンティング技術がこういう時に力を発揮する——研究者がどうやって特定したかの手法が面白い」「他の政府系AI発表も同様の疑惑がある——透明性の欠如は世界的な問題」という128コメントが展開中です。
何が起きたか
リオデジャネイロ市が「Nex-N2」を「ブラジル独自開発のAIモデル」として発表。研究者がモデル重みを分析した結果、実際には既存のオープンソースモデル（Llamaベース）の複数モデルマージであることが判明。GitHub Issueに証拠とともに投稿され拡散
モデルマージとは何か
異なるLLMの重みを数学的に合成して新しいモデルを作る手法。Mergekit等のツールで比較的簡単に実施可能。マージ自体はオープンソースライセンスが許可する範囲内であれば合法。しかし「独自開発」「ゼロから作った」と主張することは誤解を招く
モデル真正性の検証方法
研究者が使ったアプローチ：①モデル重みのコサイン類似度分析（既知モデルとの類似度測定）②ベンチマーク性能パターンの照合（特定モデルに特有の強み・弱みが一致するか）③アーキテクチャフィンガープリンティング。「AIモデルの来歴確認」という新たな調査ジャンルが生まれつつある

使用したツール・モデル

①Ollama（ollama.ai）でLLaVAをダウンロード：ollama pull llava②FFmpegで動画からフレーム抽出③llava API で各フレームをテキスト化④ChromaDB等のローカルベクトルDBに格納⑤類似検索クエリを実装。M1 Mac推奨だがCUDA GPU PCでも可能

形式検証とは何か
プログラムの正しさを数学的に証明する手法。「このコードは全ての入力に対してクラッシュしない」「この金融計算は特定の不変条件を常に満たす」という命題を自動的・半自動的に検証する。従来はロケット・医療機器等の高信頼性ソフトウェア向けだったが、ツールの成熟で一般開発にも普及しつつある
AI時代との関係

DATABASE / POSTGRESQL / PERFORMANCE — PlanetScaleエンジニアが「Postgresで唯一スケールする削除はDROP TABLEだ」という挑発的な記事を公開。108ポイント・44コメント

Postgresで唯一

PlanetScaleのエンジニアが「The only scalable delete in Postgres is DROP TABLE」というタイトルの挑発的な記事を公開し、108ポイント・44コメントを集めています。タイトルは誇張ですが、指摘している問題は非常に実践的です——Postgresで大量のレコードを削除する際のDELETE文は、テーブルが大きくなるほど深刻なパフォーマンス問題を引き起こします。MVCCアーキテクチャの仕組み上、DELETEしても実際のディスク領域はすぐに解放されず（デッドタプルとして残る）、VACUUMが走るまでテーブルが肥大化し続けます。さらにDELETE自体がロックを取り、大量削除はトランザクションを長時間占有してOLTPパフォーマンスを劣化させます。記事が提案する解決策は「パーティション分割 + パーティションDROP」というアプローチで、古いデータが特定のパーティションにまとまるようにテーブルを設計し、削除時はDELETE文ではなくALTER TABLE ... DROP PARTITION（あるいはDROP TABLE）を使うことでロックフリーかつ即時のデータ削除を実現します。HNでは「Postgres MVCCのDELETE問題はよく知られているが、これほど明快に解説した記事は少ない——チームの全員に読ませたい」「VACUUM TUNCATEとautovacuumの調整で十分では? という意見もあるが、規模による——億行を超えるとパーティション戦略は必須」「PlanetScaleはMySQL系なのでPostgresを批判したい動機もある——記事内容は正確だが文脈を理解して読む必要がある」「TimescaleDBがこのパターンをそのまま実装している——時系列データのPostgresなら最初からTimescaleを選ぶべき」という44コメントが展開中です。
なぜ大量DELETEが遅いか
PostgresのMVCC（マルチバージョン同時実行制御）では、DELETE文を実行してもデータは即座に消えない——「このタプルは削除済み」というフラグが立つだけ。実際の領域解放はVACUUMプロセスが担当。大量削除→膨大なデッドタプル→テーブルブロート→クエリ性能劣化というサイクルが起きる
推奨パターン：パーティション+DROP
日付・月などでレンジパーティションを設計→古いパーティションをDROP TABLEあるいはDETACH+DROP→即座にディスク領域解放・ロックほぼなし・VACUUMの出番なし。「過去30日分だけ保持」のようなローリングウィンドウデータに最適
どんな場合に適用すべきか
①ログ・イベント・メトリクスなど時系列データ②定期的な期限切れデータの削除が必要③テーブルが数千万〜億行規模。既存テーブルへのパーティション追加はPostgres 10以降で可能だが移行コストがある。新規テーブルは最初からパーティション設計を検討すること

菌根菌（AMF）とは
陸上植物の約80%の根に共生する微生物。植物からもらった炭素（糖）と引き換えに土壌中の水・リン・ミネラルの吸収を助ける。菌糸が地中に巨大なネットワークを形成し、異なる植物間での栄養移動も仲介する。農業・森林・気候変動において核心的な役割を持つ
